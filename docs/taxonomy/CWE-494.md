# CWE-494 — Download of code without integrity check

**Severity:** HIGH
**Frequency in Android payment code:** Low-Medium
**Languages:** Java, Kotlin

---

## Description

CWE-494 occurs when a terminal loads or executes external content —
firmware, a downloadable UI prompt file, a plugin, or a third-party
dependency — without first verifying that the content is authentic and
unmodified. Unlike CWE-347 (this taxonomy's JWT-focused signature entry),
this covers file- and package-level trust: the question is not "was this
token signed correctly" but "should this terminal be running this code or
displaying this content at all."

A payment terminal that installs an update, loads a plugin, or displays a
downloaded prompt file without checking a signature or checksum first
trusts whatever it received over the network (or from local storage) by
default. Any party able to intercept the download, compromise the
distribution server, or tamper with the file on disk can substitute
malicious content that the terminal will execute or display with full
trust.

### Direct PCI SSF relevance

- **Module B.2.8** requires that software files be cryptographically signed
  so the terminal can authenticate them before execution.
- **Module B.2.9** extends the same requirement to prompt files and other
  downloadable content — not just executable code.
- **Module C.4** (Web Software Communications) requires verifying the
  authenticity of third-party components on every fetch using cryptographic
  signatures, for any web-facing component of the software.

All three requirements share the same shape: content arrives from outside
the terminal's own trust boundary, and the terminal must verify it before
trusting it. None of them are satisfied by TLS alone — HTTPS proves the
*channel* wasn't tampered with in transit, not that the *file* wasn't
tampered with at the source or that the source is who it claims to be.

### Attack scenario

1. A payment terminal fetches a new UI prompt file (e.g. a config JSON
   defining transaction screens) from an update server on startup.
2. The download uses HTTPS, so the network transport is protected — but the
   code never checks a signature or checksum on the downloaded content
   itself.
3. An attacker who compromises the update server (or performs a supply-chain
   attack on a build pipeline that produces the file) replaces the prompt
   file with a modified one.
4. The terminal loads and displays the attacker's content with no way to
   detect the substitution — TLS validated the connection, not the payload.

## Detection logic

**Flag when:**
- A firmware update, plugin, `.dex`/`.jar` file, or executable payload is
  loaded (e.g. via `DexClassLoader`, `PathClassLoader`, direct file
  execution, or `PackageInstaller`) with no preceding signature verification
  (`Signature.verify()`) or checksum comparison against a known-good hash
- A prompt file, UI configuration file, or other downloadable content is
  fetched and used (parsed, displayed, written to a location the terminal
  will read from) with no checksum or signature check on the downloaded
  bytes before use
- A dependency, plugin, or package is fetched from a remote source and
  loaded/executed with no signature or checksum verification step

**Do NOT flag:**
- Any of the above where a `Signature.verify()` call, or a `MessageDigest`
  digest comparison against an expected hash constant, occurs on the
  downloaded/loaded bytes before they are used
- Standard Android APK installation through the Play Store or
  `PackageInstaller` using the platform's own signature enforcement — the
  OS already verifies APK signing certificates; only flag when code
  bypasses this (e.g. loading a raw `.dex` file directly via
  `DexClassLoader` instead of installing through the platform installer)
- Downloading non-executable, non-trust-affecting data (e.g. a transaction
  receipt PDF for display only, with no code path that treats it as
  trusted configuration or executable content)
- Content loaded from the app's own signed APK resources/assets — these are
  already covered by the platform's APK signature, not fetched externally

## Detection difficulty for SAST tools

| Pattern | Regex detects? | LLM detects? | Why |
|---|---|---|---|
| `DexClassLoader` used with no nearby `Signature.verify()` | Partial | Yes | Must confirm absence of a verification call anywhere in the method, not just find the loader call |
| Prompt file fetched over HTTPS, no checksum check | No | Yes | HTTPS looks "secure" superficially — must recognize that TLS doesn't substitute for payload integrity |
| Checksum comparison present but computed from the file itself (not an independent known-good value) | No | Yes | A checksum that's recomputed from the same untrusted file it's "verifying" provides no protection — requires tracing where the expected hash comes from |
| `PackageInstaller` used for standard APK install | Yes (can whitelist) | Yes | Platform enforces signing already — must not be flagged |

**CryptoGuard advantage:** the vulnerable and secure versions of a
loader/download method differ by the presence of one verification step
buried among otherwise-identical I/O code — exactly the kind of "what's
missing, not what's present" reasoning regex cannot do.

## Vulnerable patterns — Java

```java
// Pattern 1 — firmware update loaded and executed with no signature check
public void applyFirmwareUpdate(File updateFile) throws Exception {
    // FLAW: no Signature.verify() or checksum comparison before applying the update
    bootloader.flash(updateFile);
}

// Pattern 2 — downloaded prompt file used directly, no integrity check
public void refreshPromptConfig(String url) throws IOException {
    byte[] promptData = httpClient.get(url); // HTTPS, but no payload verification
    // FLAW: content is parsed and displayed with no checksum/signature check
    promptRenderer.load(promptData);
}

// Pattern 3 — plugin dex file loaded dynamically, no verification
public void loadPaymentPlugin(String dexPath) {
    // FLAW: DexClassLoader executes arbitrary code from this file with no signature check
    DexClassLoader loader = new DexClassLoader(dexPath, cacheDir, null, getClassLoader());
    Class<?> pluginClass = loader.loadClass("com.plugin.PaymentPlugin");
}

// Pattern 4 — checksum computed from the same untrusted file (no real verification)
public void applyUpdate(byte[] updateBytes) throws Exception {
    // FLAW: this "checksum" is derived from the file itself, not an independently known-good value
    String selfHash = sha256(updateBytes);
    log.info("Update checksum: " + selfHash);
    bootloader.flash(updateBytes); // No comparison against a trusted reference hash
}
```

## False positive patterns — do not flag these

```java
// FALSE POSITIVE 1 — firmware update verified with Signature.verify() before applying
public void applyFirmwareUpdate(File updateFile, PublicKey vendorKey) throws Exception {
    byte[] fileBytes = Files.readAllBytes(updateFile.toPath());
    byte[] detachedSignature = readSignatureFile(updateFile);
    Signature sig = Signature.getInstance("SHA256withRSA");
    sig.initVerify(vendorKey);
    sig.update(fileBytes);
    if (!sig.verify(detachedSignature)) {
        throw new SecurityException("Firmware signature verification failed");
    }
    bootloader.flash(updateFile); // SAFE — verified before use
}

// FALSE POSITIVE 2 — prompt file checked against an independently known-good checksum
public void refreshPromptConfig(String url, String expectedSha256) throws IOException {
    byte[] promptData = httpClient.get(url);
    String actualHash = sha256(promptData);
    if (!actualHash.equals(expectedSha256)) { // expectedSha256 comes from a trusted manifest, not this file
        throw new SecurityException("Prompt file integrity check failed");
    }
    promptRenderer.load(promptData); // SAFE
}

// FALSE POSITIVE 3 — standard Play Store / PackageInstaller APK install
public void installUpdate(Uri apkUri) {
    PackageInstaller installer = pm.getPackageInstaller();
    // SAFE — platform enforces APK signature verification during install
    installer.openSession(sessionId).commit(intentSender);
}

// FALSE POSITIVE 4 — non-executable, non-trusted-config content
public void downloadReceipt(String url) {
    byte[] pdfBytes = httpClient.get(url);
    receiptViewer.display(pdfBytes); // SAFE — display-only, not executed or trusted as config
}
```

## Secure alternatives

```java
// Option 1 — detached signature verification (recommended for firmware/plugins)
public void applyFirmwareUpdate(File updateFile, PublicKey vendorKey, byte[] signature) throws Exception {
    byte[] fileBytes = Files.readAllBytes(updateFile.toPath());
    Signature sig = Signature.getInstance("SHA256withRSA");
    sig.initVerify(vendorKey);
    sig.update(fileBytes);
    if (!sig.verify(signature)) {
        throw new SecurityException("Signature verification failed — refusing to apply update");
    }
    bootloader.flash(updateFile);
}

// Option 2 — checksum against a value from a separately-signed manifest
public void refreshPromptConfig(String url, Manifest signedManifest) throws IOException {
    byte[] promptData = httpClient.get(url);
    String expectedHash = signedManifest.getVerifiedHashFor(url); // manifest itself was signature-checked
    if (!sha256(promptData).equals(expectedHash)) {
        throw new SecurityException("Prompt file does not match manifest checksum");
    }
    promptRenderer.load(promptData);
}

// Option 3 — use the platform installer instead of a raw DexClassLoader
public void installPlugin(Uri apkUri) {
    // Let the OS enforce APK signature verification rather than dynamically loading unverified dex
    PackageInstaller installer = pm.getPackageInstaller();
    installer.openSession(sessionId).commit(intentSender);
}
```

```kotlin
// Kotlin — signature verification before loading a dependency
fun loadRemoteDependency(url: String, vendorKey: PublicKey, signature: ByteArray) {
    val jarBytes = httpClient.download(url)
    val sig = Signature.getInstance("SHA256withRSA")
    sig.initVerify(vendorKey)
    sig.update(jarBytes)
    check(sig.verify(signature)) { "Dependency signature verification failed" }
    val tempFile = File(cacheDir, "dep.jar").apply { writeBytes(jarBytes) }
    val loader = DexClassLoader(tempFile.path, cacheDir.path, null, javaClass.classLoader)
}
```
