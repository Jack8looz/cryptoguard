# CWE-347 — Improper verification of cryptographic signature

**Severity:** CRITICAL  
**Frequency in Android payment code:** Medium  
**Languages:** Java, Kotlin, Python (pipeline/backend)  

---

## Description

A cryptographic signature proves two things: that a message was created by
a trusted party who holds the private key, and that the message has not been
tampered with since it was signed. CWE-347 occurs when an application accepts
a signed artifact — most commonly a JWT — without actually verifying the
signature.

The result is that the signature provides zero security. An attacker can
forge any token, claim any identity, escalate to any privilege level, and
the application accepts it as completely valid with no error, no log entry,
and no indication that anything is wrong.

### JWT structure and the verification requirement

A JSON Web Token has three Base64-encoded parts separated by dots:

```
header.payload.signature
```

- **Header:** algorithm used (e.g. HS256, RS256) and token type
- **Payload:** claims — user ID, roles, expiry, issued-at timestamp
- **Signature:** HMAC or RSA signature over header + payload

The signature is the only thing that makes a JWT trustworthy. Without
verification, the payload can contain anything the attacker chooses.

### Direct relevance to payment terminals

A payment terminal that accepts JWTs for authentication or authorization
without verifying signatures allows any attacker to:

1. Decode any legitimate JWT (they are Base64 encoded, not encrypted)
2. Modify the payload — change user ID, elevate role to admin, extend expiry
3. Re-encode the token without a valid signature
4. Present the forged token — the terminal accepts it as valid

This gives an attacker complete control over authentication and authorization
in the payment flow.

### The "alg: none" attack

A related attack exploits JWT libraries that accept the algorithm field
from the token header itself. An attacker sets `"alg": "none"` in the
header, removes the signature entirely, and some libraries accept the
token because "none" means no signature required. This is not a theoretical
attack — it has been exploited in production systems and was documented by
Auth0 in 2015 as a critical vulnerability affecting multiple JWT libraries.

## Why this is the strongest detection case in this taxonomy

This vulnerability is completely invisible to regex-based SAST tools.
The vulnerable and secure code are nearly identical — the only difference
is the presence or absence of an options parameter, a method name, or a
boolean flag. There is no forbidden string to match.

An LLM reading the code understands that:
- `parseClaimsJws()` with a key verifies the signature — safe
- `parseClaimsJwt()` does not verify — vulnerable
- `parserBuilder().build()` without a key followed by `parseClaimsJws()` — vulnerable
- `JWT.decode()` just decodes without verifying — vulnerable
- `JWT.require(Algorithm.HMAC256(secret)).build().verify()` — safe
- `options={"verify_signature": False}` explicitly disables verification — critical
- `algorithms=["none"]` accepts unsigned tokens — critical

No regex, no AST pattern, no rule engine can detect the semantic difference
between these method names without understanding what each one does.

| Pattern | Regex detects? | LLM detects? | Why |
|---|---|---|---|
| `verify_signature: False` | Partial | Yes | LLM understands the security implication |
| `parseClaimsJwt()` vs `parseClaimsJws()` | No | Yes | Must know jjwt API semantics |
| `parserBuilder().build()` without key | No | Yes | Must detect absent signing key |
| `JWT.decode()` without verifier | No | Yes | Must know Auth0 API — decode ≠ verify |
| `algorithms=["none"]` | No | Yes | Must understand "none" disables verification |
| `JWT.require(Algorithm.none())` | No | Yes | Must recognize none algorithm as insecure |
| Swallowed `SignatureException` | No | Yes | Must trace exception handling flow |
| Correct `parseClaimsJws()` with key | N/A | Yes | Correctly identifies as safe |

**CryptoGuard advantage:** this is the clearest demonstration in the entire
project of why LLM-based analysis beats pattern matching. The difference
between secure and vulnerable code is semantic, not syntactic.

## Vulnerable patterns — Java (jjwt library)

```java
// Pattern 1 — parseClaimsJwt() does not verify signature
// Most common mistake with the jjwt library
Claims claims = Jwts.parser()
    .parseClaimsJwt(token)  // VULNERABLE — no signature verification
    .getBody();

// Pattern 2 — keyless parser (most insidious pattern)
// Developer uses the correct method name but omits the signing key
// Some library versions silently skip verification when no key is set
JwtParser parser = Jwts.parserBuilder()
    .build();              // No .setSigningKey() call
Claims claims = parser
    .parseClaimsJws(token) // Looks correct — but no key means no verification
    .getBody();

// Pattern 3 — parseClaimsJws() without setSigningKey()
Claims claims = Jwts.parser()
    .parseClaimsJws(token)  // No key set — verification silently skipped
    .getBody();

// Pattern 4 — alg:none attack — accepting unsigned tokens
JWTVerifier verifier = JWT.require(Algorithm.none()).build(); // VULNERABLE
DecodedJWT jwt = verifier.verify(token);

// Pattern 5 — manual Base64 decode without signature check
String[] parts = token.split("\\.");
String payload = new String(Base64.getDecoder().decode(parts[1]));
JSONObject claims = new JSONObject(payload); // Signature never checked

// Pattern 6 — catching and ignoring SignatureException
try {
    Claims claims = Jwts.parser()
        .setSigningKey(secret)
        .parseClaimsJws(token)
        .getBody();
} catch (SignatureException e) {
    // Swallowing exception and re-parsing without verification
    claims = Jwts.parser().parseClaimsJwt(token).getBody(); // VULNERABLE
}
```

## Vulnerable patterns — Java (Auth0 java-jwt library)

```java
// Pattern 1 — JWT.decode() just decodes, does NOT verify signature
// Developers often confuse this with verification
DecodedJWT jwt = JWT.decode(token); // VULNERABLE — no signature check
String userId = jwt.getSubject();   // Claims accepted without verification

// Pattern 2 — Algorithm.none() in verifier
JWTVerifier verifier = JWT.require(Algorithm.none()).build(); // VULNERABLE
DecodedJWT jwt = verifier.verify(token); // Accepts unsigned tokens
```

## Vulnerable patterns — Kotlin

```kotlin
// Pattern 1 — parseClaimsJwt() without verification
val claims = Jwts.parser()
    .parseClaimsJwt(token) // VULNERABLE
    .body

// Pattern 2 — keyless parser builder
val parser = Jwts.parserBuilder().build() // No signing key
val claims = parser.parseClaimsJws(token).body // Verification skipped

// Pattern 3 — Auth0 JWT.decode() without verifier
val jwt = JWT.decode(token) // VULNERABLE — just decodes
val userId = jwt.subject

// Pattern 4 — swallowed SignatureException
try {
    val claims = Jwts.parser()
        .setSigningKey(secret)
        .parseClaimsJws(token)
        .body
} catch (e: SignatureException) {
    // Continuing with unverified token
    val claims = Jwts.parser().parseClaimsJwt(token).body // VULNERABLE
}
```

## Vulnerable patterns — Python (backend/pipeline)

```python
# Pattern 1 — PyJWT with verification disabled
import jwt
claims = jwt.decode(
    token,
    options={"verify_signature": False}  # CRITICAL — signature never checked
)

# Pattern 2 — algorithms=["none"] accepted
claims = jwt.decode(token, algorithms=["none"])  # CRITICAL

# Pattern 3 — decode without key (older PyJWT versions)
claims = jwt.decode(token, key="")  # Empty key — verification may be skipped
```

## False positive patterns — do not flag these

```java
// FALSE POSITIVE 1 — jjwt parseClaimsJws() with signing key (correct)
Claims claims = Jwts.parserBuilder()
    .setSigningKey(key)           // Key is set
    .build()
    .parseClaimsJws(token)        // Safe — signature IS verified
    .getBody();

// FALSE POSITIVE 2 — Auth0 JWT.require() with real algorithm (correct)
JWTVerifier verifier = JWT.require(Algorithm.HMAC256(secret))
    .withIssuer("payment-server")
    .build();
DecodedJWT jwt = verifier.verify(token); // Safe — verifies signature

// FALSE POSITIVE 3 — RSA public key verification
Claims claims = Jwts.parserBuilder()
    .setSigningKey(rsaPublicKey)  // RSA public key for RS256 verification
    .build()
    .parseClaimsJws(token)        // Safe
    .getBody();

// FALSE POSITIVE 4 — JWT.decode() used for logging only after prior verification
// Safe only if token was already verified earlier in the pipeline
DecodedJWT decoded = JWT.decode(verifiedToken); // Safe in this context
log.info("Processing token for subject: " + decoded.getSubject());
```

```python
# FALSE POSITIVE 5 — PyJWT with key and algorithm (correct)
claims = jwt.decode(token, key, algorithms=["HS256"])  # Safe — verifies by default
```

## Secure alternatives

```java
// jjwt — always use parserBuilder() with setSigningKey()
SecretKey key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(secretString));

Claims claims = Jwts.parserBuilder()
    .setSigningKey(key)           // Must be set before build()
    .build()
    .parseClaimsJws(token)        // parseClaimsJws — not parseClaimsJwt
    .getBody();

// Always validate expiry after parsing
if (claims.getExpiration().before(new Date())) {
    throw new SecurityException("Token expired");
}

// Auth0 java-jwt — use JWT.require() with real algorithm, never JWT.decode()
JWTVerifier verifier = JWT.require(Algorithm.HMAC256(secret))
    .withIssuer("payment-server")
    .withAudience("terminal")
    .build();
DecodedJWT jwt = verifier.verify(token); // Verifies signature + claims

// RSA — verify with public key for RS256
JWTVerifier verifier = JWT.require(Algorithm.RSA256(rsaPublicKey, null))
    .build();
DecodedJWT jwt = verifier.verify(token);
```

```kotlin
// Kotlin — jjwt secure usage
val key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(secretString))

val claims = Jwts.parserBuilder()
    .setSigningKey(key)
    .build()
    .parseClaimsJws(token)
    .body

require(!claims.expiration.before(Date())) { "Token expired" }
```

```python
# Python — PyJWT secure usage
# Signature is verified by default when key and algorithms are provided
claims = jwt.decode(token, key, algorithms=["HS256"])

# Never pass options={"verify_signature": False}
# Never include "none" in algorithms list
```
