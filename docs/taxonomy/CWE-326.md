# CWE-326 — Inadequate encryption strength

**Severity:** HIGH  
**Frequency in Android payment code:** Medium  
**Languages:** Java, Kotlin  

---

## Description

Encryption strength is directly determined by key size. A key that is too
short can be broken by brute-force or mathematical attacks using modern
hardware. This CWE occurs when a key is generated with a size below the
currently accepted minimum for its algorithm.

Key size minimums as of 2025 per NIST SP 800-131A:

| Algorithm | Broken — never use | Weak — avoid | Minimum acceptable | Recommended |
|---|---|---|---|---|
| RSA | < 1024 bits | 1024 bits | 2048 bits | 4096 bits |
| AES | < 128 bits | — | 128 bits | 256 bits |
| EC (ECDH/ECDSA) | < 224 bits | 224 bits | 256 bits | 384 bits |
| DSA | < 1024 bits | 1024 bits | 2048 bits | Migrate to EC |
| 3DES | All sizes | — | Deprecated 2023 | Migrate to AES |

### Direct relevance to this project

This company uses RSA for backend communication. Any RSA key generated with
fewer than 2048 bits must be flagged immediately — RSA-512 can be factored
in hours on commodity hardware, and RSA-1024 is considered broken by NIST.
A compromised RSA key exposes all backend communication.

## Why RSA-512 is broken — attack feasibility

| RSA key size | Factoring cost (2025 hardware) | Status |
|---|---|---|
| 512 bits | Hours on consumer hardware | Broken |
| 768 bits | Weeks on cloud computing | Broken |
| 1024 bits | Months to years for a well-funded attacker | Weak — NIST deprecated |
| 2048 bits | Computationally infeasible | Acceptable |
| 4096 bits | Far beyond current capability | Recommended |

**Reference:** In 2009, researchers factored RSA-768 using hundreds of machines
over 2 years. In 2025, cloud computing and improved algorithms make RSA-1024
feasible for nation-state or well-funded attackers. RSA-512 is trivially broken
by any motivated attacker with a consumer PC.

---

## Future considerations — post-quantum cryptography

| Algorithm | Quantum attack | Status in quantum era |
|---|---|---|
| RSA (any size) | Shor's algorithm — polynomial time | Broken |
| EC (any curve) | Shor's algorithm — polynomial time | Broken |
| AES-128 | Grover's algorithm — 64-bit effective | Weakened |
| AES-256 | Grover's algorithm — 128-bit effective | Safe for now |

**For payment terminals:** while large-scale quantum computers do not yet
exist, sensitive long-term data such as customer PII and historical
transaction records should use AES-256. NIST finalized post-quantum
standards in 2024 — CRYSTALS-Kyber (now ML-KEM) for key encapsulation
and CRYSTALS-Dilithium (now ML-DSA) for signatures. Flag any new RSA or
EC implementations as candidates for future migration.

## Detection logic

This CWE has the simplest detection logic in the taxonomy — it is a direct
numerical comparison or curve name lookup. Minimal context analysis required.

**Flag when:**
- RSA key size < 2048 bits
- AES key size < 128 bits
- EC key size < 256 bits, or curve name maps to fewer than 256 bits
- DSA key size < 2048 bits
- Any key size of 0 or clearly placeholder values

**The only false positive risk:** test classes using small keys for speed.
Flag these at WARNING severity rather than CRITICAL when inside a `@Test`
annotated method or a class whose name contains "Test".

## ECC curve name reference

Android's `KeyPairGenerator` accepts curve names via `ECGenParameterSpec`
instead of bit sizes. The AI must map curve names to their bit strength:

| Curve name | Bit strength | Status |
|---|---|---|
| secp112r1 | 112 bits | Broken — never use |
| secp128r1 | 128 bits | Broken — never use |
| secp160r1 | 160 bits | Weak — below NIST minimum |
| secp192r1 / prime192v1 | 192 bits | Weak — below NIST minimum |
| secp224r1 | 224 bits | Marginal — NIST deprecated for new use |
| secp256r1 / prime256v1 / P-256 | 256 bits | Acceptable — NIST minimum |
| secp384r1 / P-384 | 384 bits | Recommended |
| secp521r1 / P-521 | 521 bits | Strong |

## Detection difficulty for SAST tools

| Pattern | Regex detects? | LLM detects? | Why |
|---|---|---|---|
| `kpg.initialize(512)` | Yes | Yes | Direct number extraction |
| `kpg.initialize(keySize)` variable | No | Yes | Must trace variable value |
| `ECGenParameterSpec("secp112r1")` | No | Yes | Must map curve name to bit strength |
| `setKeySize(1024)` in KeyStore | Partial | Yes | Needs to know 1024 is weak for RSA |
| Small key in test class | Partial | Yes | LLM reduces severity for test context |
| AES-128 flagged as weak | N/A | Yes | LLM correctly does not flag AES-128 |

---

## Why an LLM detects this better than regex

A regex tool can extract the number `512` from `kpg.initialize(512)` but:

- Cannot map `ECGenParameterSpec("secp112r1")` to its 112-bit strength
  without a curve name lookup table
- Cannot trace a variable `int KEY_SIZE = 1024` used later in `kpg.initialize(KEY_SIZE)`
- Cannot distinguish RSA-512 (broken) from AES-128 (acceptable) without
  knowing which algorithm is being used
- Cannot correctly handle `setKeySize()` inside an Android `KeyGenParameterSpec`
  builder without understanding the builder pattern

An LLM with the curve name table embedded in its prompt handles all of these.

## Vulnerable patterns — Java

```java
// Pattern 1 — RSA key too short (broken)
KeyPairGenerator kpg = KeyPairGenerator.getInstance("RSA");
kpg.initialize(512);  // Broken — factorable in hours
kpg.initialize(1024); // Weak — NIST deprecated

// Pattern 2 — RSA with SecureRandom but still insufficient size
KeyPairGenerator kpg = KeyPairGenerator.getInstance("RSA");
kpg.initialize(512, new SecureRandom()); // SecureRandom does not fix key size

// Pattern 3 — AES key too short
KeyGenerator keyGen = KeyGenerator.getInstance("AES");
keyGen.init(64); // Broken
keyGen.init(56); // Broken

// Pattern 4 — EC key size too small (numeric)
KeyPairGenerator kpg = KeyPairGenerator.getInstance("EC");
kpg.initialize(160); // Below NIST minimum of 256

// Pattern 5 — EC weak curve by name
KeyPairGenerator kpg = KeyPairGenerator.getInstance("EC");
kpg.initialize(new ECGenParameterSpec("secp112r1")); // 112-bit — broken
kpg.initialize(new ECGenParameterSpec("secp160r1")); // 160-bit — weak
kpg.initialize(new ECGenParameterSpec("secp192r1")); // 192-bit — weak

// Pattern 6 — Android KeyStore with weak RSA key size
// Payment terminal specific — common in production Android code
KeyGenParameterSpec spec = new KeyGenParameterSpec.Builder(
    "payment_key",
    KeyProperties.PURPOSE_ENCRYPT | KeyProperties.PURPOSE_DECRYPT)
    .setKeySize(1024)  // Weak — minimum is 2048
    .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_RSA_PKCS1)
    .build();

// Pattern 7 — DSA key too short (if present in legacy code)
KeyPairGenerator kpg = KeyPairGenerator.getInstance("DSA");
kpg.initialize(512);  // Broken
kpg.initialize(1024); // Weak — NIST deprecated

// Pattern 8 — key size stored in variable
int KEY_SIZE = 1024; // Defined as constant
KeyPairGenerator kpg = KeyPairGenerator.getInstance("RSA");
kpg.initialize(KEY_SIZE); // LLM must trace KEY_SIZE to its value
```

## False positive patterns — do not flag these

```java
// FALSE POSITIVE 1 — RSA-2048 (minimum acceptable)
KeyPairGenerator kpg = KeyPairGenerator.getInstance("RSA");
kpg.initialize(2048); // Acceptable — meets NIST minimum

// FALSE POSITIVE 2 — AES-128 (acceptable)
KeyGenerator keyGen = KeyGenerator.getInstance("AES");
keyGen.init(128); // Acceptable — AES-128 is still secure

// FALSE POSITIVE 3 — EC-256 with acceptable curve name
KeyPairGenerator kpg = KeyPairGenerator.getInstance("EC");
kpg.initialize(new ECGenParameterSpec("secp256r1")); // Acceptable — NIST P-256

// FALSE POSITIVE 4 — small key in test class for performance
@Test
public void testRsaEncryption() {
    KeyPairGenerator kpg = KeyPairGenerator.getInstance("RSA");
    kpg.initialize(512); // WARNING only — test context, but should still be fixed
}

// FALSE POSITIVE 5 — EC-384 recommended curve
kpg.initialize(new ECGenParameterSpec("secp384r1")); // Recommended — safe
```

## Secure alternatives

```java
// RSA — minimum 2048, recommended 4096
KeyPairGenerator kpg = KeyPairGenerator.getInstance("RSA");
kpg.initialize(4096, new SecureRandom());
KeyPair keyPair = kpg.generateKeyPair();

// AES — minimum 128, recommended 256
KeyGenerator keyGen = KeyGenerator.getInstance("AES");
keyGen.init(256, new SecureRandom());
SecretKey key = keyGen.generateKey();

// EC — use secp256r1 minimum, secp384r1 recommended
KeyPairGenerator kpg = KeyPairGenerator.getInstance("EC");
kpg.initialize(new ECGenParameterSpec("secp384r1"), new SecureRandom());
KeyPair keyPair = kpg.generateKeyPair();

// Android KeyStore — correct key size for RSA
KeyGenParameterSpec spec = new KeyGenParameterSpec.Builder(
    "payment_key",
    KeyProperties.PURPOSE_ENCRYPT | KeyProperties.PURPOSE_DECRYPT)
    .setKeySize(4096)  // Strong RSA key
    .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_RSA_OAEP)
    .build();

// DSA legacy migration — replace with EC
// Instead of DSA, use EC for equivalent security with smaller key sizes
KeyPairGenerator kpg = KeyPairGenerator.getInstance("EC");
kpg.initialize(new ECGenParameterSpec("secp256r1"), new SecureRandom());
```

```kotlin
// Kotlin secure alternatives
val kpg = KeyPairGenerator.getInstance("RSA")
kpg.initialize(4096, SecureRandom())
val keyPair = kpg.generateKeyPair()

val keyGen = KeyGenerator.getInstance("AES")
keyGen.init(256, SecureRandom())
val key = keyGen.generateKey()

val ecKpg = KeyPairGenerator.getInstance("EC")
ecKpg.initialize(ECGenParameterSpec("secp384r1"), SecureRandom())
val ecKeyPair = ecKpg.generateKeyPair()
```
