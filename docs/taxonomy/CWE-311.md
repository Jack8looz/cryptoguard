# CWE-311 — Missing encryption of sensitive data

**Severity:** CRITICAL  
**Frequency in Android payment code:** Medium  
**Languages:** Java, Kotlin  

---

## Description

CWE-311 occurs when sensitive data is stored or transmitted without any
encryption. Unlike CWE-327 (wrong algorithm) or CWE-329 (weak IV), this
vulnerability requires no cryptographic knowledge to introduce — the
developer simply never applied encryption at all.

The vulnerability is defined by absence, not by presence. There is no
broken algorithm to flag, no weak parameter to detect — only sensitive
data flowing through an unprotected channel or being written to an
unprotected location.

### Relationship to child CWEs

CWE-311 is a parent weakness with two more specific children. For Phase 3
implementation, detect these as distinct subtypes with separate detection
rules and more precise output:

| CWE | Name | Detection focus |
|---|---|---|
| **CWE-312** | Cleartext storage of sensitive information | SharedPreferences, SQLite, files, logs |
| **CWE-319** | Cleartext transmission of sensitive information | HTTP URLs, unencrypted sockets |

When your tool detects a storage issue, report `CWE-312`. When it detects
a transmission issue, report `CWE-319`. Report the parent `CWE-311` only
when the context does not clearly distinguish between the two.

### What counts as sensitive data

For a payment terminal application, sensitive data includes:

| Data type | Examples |
|---|---|
| Payment data | card numbers, CVV, PAN, transaction amounts |
| Authentication | passwords, PINs, session tokens, JWT values |
| Personal data | customer name, address, national ID, phone number |
| Cryptographic material | private keys, symmetric keys, certificates |
| Banking data | account numbers, IBAN, bank codes |

### Storage vs transmission

**Insecure storage (CWE-312):** sensitive data written to SharedPreferences,
SQLite, files, or logs without encryption. On a rooted Android device or
after physical access to the terminal, this data is directly readable.

**Insecure transmission (CWE-319):** sensitive data sent over HTTP instead
of HTTPS, written to a network socket without TLS, or logged and transmitted
to a remote logging service without encryption.

---

## Why this is the hardest CWE to detect

Every other CWE in this taxonomy has a positive signal — a method call,
an algorithm name, a parameter value. CWE-311 is detected by the absence
of a signal. The AI must:

1. Identify that the data being handled is sensitive
2. Verify that no encryption is applied before storage or transmission
3. Distinguish between data that genuinely has no protection and data
   that is protected earlier in the call chain

This requires the deepest contextual reasoning of any CWE in the taxonomy.
It is included as a Tier 3 detection target — meaning it should be
implemented after the Tier 1 and Tier 2 CWEs are stable, and its
false positive rate will be higher.

## Detection logic

**Flag as CWE-312 (storage) when:**
- A variable containing sensitive data is written to SharedPreferences,
  a file, SQLite, or a log without an encryption call in the same code path
- Sensitive data appears in a `Log.d()`, `Log.e()`, `Log.w()`, or
  `System.out.println()` call

**Flag as CWE-319 (transmission) when:**
- An HTTP URL (not HTTPS) is used for a connection that transmits sensitive data
- A network socket is opened without TLS and sensitive data is written to it

**Signals that indicate sensitive data:**
- Variable names: `password`, `pin`, `cardNumber`, `cvv`, `pan`, `token`,
  `privateKey`, `secret`, `ssn`, `accountNumber`, `iban`
- Method context: `processPayment()`, `authenticate()`, `storeCredentials()`
- Class context: `PaymentActivity`, `LoginManager`, `CardProcessor`

**Do not flag when:**
- Data is encrypted before storage — even if the encryption has issues
  (those are CWE-327 or CWE-329, not CWE-311)
- HTTPS is used for transmission
- Data is a non-sensitive value stored in the same location
- Sensitive data appears in a test or mock context

## Detection difficulty for SAST tools

| Pattern | Regex detects? | LLM detects? | Why |
|---|---|---|---|
| `putString("password", plaintext)` | Partial | Yes | Must recognize value as sensitive |
| `Log.d("TAG", password)` | No | Yes | Must recognize log as insecure output |
| HTTP URL with payment data | No | Yes | Must recognize HTTP as unencrypted |
| SQLite insert of card number | No | Yes | Must recognize column as sensitive |
| Log injection via user-controlled input | No | Yes | Must trace attacker-controlled data to log |
| Data encrypted before storage | N/A | Yes | Correctly identifies as not CWE-311 |
| Non-sensitive data in SharedPrefs | N/A | Yes | Correctly ignores non-sensitive data |

---

## Why an LLM detects this better than regex

A regex tool searching for `SharedPreferences.putString` would flag every
string written to preferences regardless of sensitivity. An LLM reads the
variable name, surrounding method name, and class context to determine
whether the value is sensitive.

The second hard case is the absent encryption — there is no string to match.
An LLM reading:

```java
prefs.putString("user_pin", pin);
```

understands that `pin` is sensitive payment data, that `putString` writes
to SharedPreferences in plaintext, and that no encryption call precedes
this line. All three conclusions require semantic reasoning.

## Vulnerable patterns — Java

```java
// Pattern 1 — PIN stored in SharedPreferences without encryption (CWE-312)
SharedPreferences prefs = getSharedPreferences("app_prefs", MODE_PRIVATE);
prefs.edit().putString("user_pin", pin).apply(); // Plaintext PIN on disk

// Pattern 2 — sensitive data logged in plaintext (CWE-312)
Log.d("AuthManager", "User password: " + password); // Written to logcat

// Pattern 3 — log injection via attacker-controlled input (CWE-312)
// Attacker enters PIN: "1234\n[INFO] Transaction approved\n"
// Forged entries appear in log output
Log.e("Payment", "Invalid PIN attempt: " + pin); // Attacker controls pin value

// Pattern 4 — card number written to a file (CWE-312)
FileOutputStream fos = openFileOutput("card_data.txt", MODE_PRIVATE);
fos.write(cardNumber.getBytes()); // Plaintext card number on disk

// Pattern 5 — sensitive data sent over HTTP (CWE-319)
URL url = new URL("http://payment-server.com/transaction"); // HTTP — no TLS
HttpURLConnection conn = (HttpURLConnection) url.openConnection();
conn.getOutputStream().write(transactionData.getBytes());

// Pattern 6 — session token stored in SharedPreferences (CWE-312)
prefs.edit().putString("session_token", jwtToken).apply();

// Pattern 7 — SQLite insert of sensitive data without encryption (CWE-312)
ContentValues values = new ContentValues();
values.put("card_number", cardNumber); // Plaintext in database
values.put("cvv", cvv);
db.insert("payments", null, values);

// Pattern 8 — private key written to a regular file (CWE-312)
FileOutputStream fos = new FileOutputStream("private_key.pem");
fos.write(privateKey.getEncoded()); // Key material on unprotected disk

// Pattern 9 — sensitive data in exception message (CWE-312)
// Exception messages appear in crash reports and remote logging services
throw new RuntimeException("Authentication failed for PIN: " + pin);
```

## Vulnerable patterns — Kotlin

```kotlin
// Pattern 1 — PIN in SharedPreferences (CWE-312)
getSharedPreferences("prefs", MODE_PRIVATE)
    .edit()
    .putString("pin", userPin) // Plaintext PIN
    .apply()

// Pattern 2 — password logged (CWE-312)
Log.e("Login", "Failed login with password: $password")

// Pattern 3 — HTTP transmission (CWE-319)
val url = URL("http://bank-api.company.com/verify") // HTTP — unencrypted
val conn = url.openConnection() as HttpURLConnection
conn.outputStream.write(accountData.toByteArray())

// Pattern 4 — card data in SQLite (CWE-312)
val values = ContentValues().apply {
    put("card_number", cardNumber) // Plaintext
    put("expiry", expiryDate)
}
db.insert("transactions", null, values)

// Pattern 5 — sensitive data in log (CWE-312)
Log.d("PAYMENT", "Processing card: $cardNumber amount: $amount")
```

## False positive patterns — do not flag these

```java
// FALSE POSITIVE 1 — data encrypted before storage
String encrypted = encryptWithAesGcm(pin, secretKey); // Encrypted first
prefs.edit().putString("user_pin", encrypted).apply(); // Safe — already encrypted
// Note: the encryption itself may have other issues but this is not CWE-311

// FALSE POSITIVE 2 — HTTPS transmission
URL url = new URL("https://payment-server.com/transaction"); // Safe

// FALSE POSITIVE 3 — non-sensitive data in SharedPreferences
prefs.edit().putString("theme", "dark").apply();    // Not sensitive
prefs.edit().putString("language", "fr").apply();   // Not sensitive

// FALSE POSITIVE 4 — Android KeyStore for key storage
KeyStore ks = KeyStore.getInstance("AndroidKeyStore");
ks.setEntry("my_key", keyEntry, null); // Hardware-backed — safe

// FALSE POSITIVE 5 — hashed password stored (not plaintext)
String hashed = BCrypt.hashpw(password, BCrypt.gensalt(12));
prefs.edit().putString("password_hash", hashed).apply(); // Safe — hashed

// FALSE POSITIVE 6 — logging non-sensitive identifier only
Log.d("AuthManager", "Login attempt for userId: " + userId); // Safe — ID only
```

## Secure alternatives

```java
// Option 1 — Android EncryptedSharedPreferences (recommended for Android)
MasterKey masterKey = new MasterKey.Builder(context)
    .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
    .build();

SharedPreferences encryptedPrefs = EncryptedSharedPreferences.create(
    context,
    "secure_prefs",
    masterKey,
    EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
    EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
);
encryptedPrefs.edit().putString("user_pin", pin).apply();

// Option 2 — Android 12+ StrongBox hardware keystore for high-value keys
// StrongBox provides hardware-level isolation in a dedicated security chip
KeyGenParameterSpec spec = new KeyGenParameterSpec.Builder(
    "payment_key",
    KeyProperties.PURPOSE_ENCRYPT | KeyProperties.PURPOSE_DECRYPT)
    .setKeySize(256)
    .setIsStrongBoxBacked(true)      // Backed by dedicated hardware security module
    .setUserAuthenticationRequired(true) // Requires biometric or PIN to use
    .build();
// Use this for the highest-value keys — payment master keys, PIN encryption keys

// Option 3 — encrypt before writing to SQLite
String encryptedCard = encryptWithAesGcm(cardNumber, secretKey);
values.put("card_number", encryptedCard); // Encrypted column

// Option 4 — always HTTPS, enforce in network security config
URL url = new URL("https://payment-server.com/transaction");
// Also add network_security_config.xml to block all cleartext traffic:
// <base-config cleartextTrafficPermitted="false"/>

// Option 5 — never log sensitive data
// Log only non-sensitive context like user ID, timestamp, or error code
if (BuildConfig.DEBUG) {
    Log.d("Auth", "Login attempt — userId: " + userId + " result: " + result);
}
// Strip all debug logs in production via ProGuard/R8 rule:
// -assumenosideeffects class android.util.Log { *; }
```

```kotlin
// Kotlin — EncryptedSharedPreferences
val masterKey = MasterKey.Builder(context)
    .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
    .build()

val encryptedPrefs = EncryptedSharedPreferences.create(
    context,
    "secure_prefs",
    masterKey,
    EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
    EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
)
encryptedPrefs.edit().putString("user_pin", pin).apply()

// Kotlin — Android 12+ StrongBox
val spec = KeyGenParameterSpec.Builder(
    "payment_key",
    KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
    .setKeySize(256)
    .setIsStrongBoxBacked(true)
    .setUserAuthenticationRequired(true)
    .build()
```

## Expected AI output format

For PIN stored in SharedPreferences:

```json
{
  "vulnerable": true,
  "cwe": "CWE-311",
  "specific_cwe": "CWE-312",
  "severity": "CRITICAL",
  "explanation": "A PIN is stored in SharedPreferences without encryption.
                  SharedPreferences files are readable on rooted devices and
                  during physical access to the terminal. Use
                  EncryptedSharedPreferences to encrypt both keys and values
                  at rest.",
  "fix_code": "MasterKey masterKey = new MasterKey.Builder(context)\n    .setKeyScheme(MasterKey.KeyScheme.AES256_GCM).build();\nSharedPreferences prefs = EncryptedSharedPreferences.create(\n    context, \"secure_prefs\", masterKey, AES256_SIV, AES256_GCM);"
}
```

For sensitive data logged:

```json
{
  "vulnerable": true,
  "cwe": "CWE-311",
  "specific_cwe": "CWE-312",
  "severity": "HIGH",
  "explanation": "A password is written to Android logcat. Log output is
                  accessible to other apps with READ_LOGS permission, may be
                  captured by crash reporting tools, and is vulnerable to log
                  injection if the value is attacker-controlled. Never log

  "fix_code": "// Remove log statement. Log only non-sensitive context:\nLog.d(\"AuthManager\", \"Login attempt for userId: \" + userId);"
```

