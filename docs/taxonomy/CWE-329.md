# CWE-329 — Generation of predictable IV with CBC mode

**Severity:** HIGH  
**Frequency in Android payment code:** High  
**Languages:** Java, Kotlin  

---

## Description

An Initialization Vector (IV) is a random value combined with the first block
of plaintext before CBC encryption begins. Its purpose is to ensure that
encrypting the same data twice with the same key produces different ciphertext
each time — this property is called semantic security or IND-CPA security.

CWE-329 occurs when the IV is:
- **Zeroed:** `new byte[8]` or `new byte[16]` — all zeros, fully predictable
- **Hardcoded:** a fixed byte sequence in source code
- **Reused:** generated once and used across multiple encryption operations

**Why reuse breaks security even with a random IV:**
Reusing the same IV with the same key creates a deterministic relationship
between plaintext blocks. Identical plaintext blocks encrypted with the same
key and IV produce identical ciphertext blocks — an attacker observing multiple
ciphertexts can detect repeated content and in some scenarios partially recover
plaintext. The indistinguishability property of CBC is completely destroyed.

### Direct relevance to this project

This company uses 3DES in CBC mode for bank communication. 3DES-CBC requires
an 8-byte IV. If any part of the codebase initializes this IV as `new byte[8]`
or reuses a session-level IV across multiple payment transactions, every
transaction is potentially leakable to a network observer. This must be
flagged as HIGH severity even in the legacy bank communication context.

---

## Real-world impact — the BEAST attack (2011)

In SSL 3.0 and TLS 1.0, IVs for CBC mode were chained from the previous
ciphertext block, making them predictable. Attackers exploited this to
decrypt HTTPS cookies in under 10 minutes using a chosen-plaintext attack.
The attack forced the industry to deprecate TLS 1.0 and CBC mode for
many applications.

**Relevance to payment code:** the same principle applies — predictable IVs
in 3DES-CBC bank communication could allow an attacker with network access
to decrypt transaction details incrementally by observing patterns across
multiple encrypted messages.

## NIST SP 800-38A — two acceptable methods for CBC IV generation

| Method | Implementation | Security property |
|---|---|---|
| Random | Generate fresh random bytes for each encryption operation | Unpredictable |
| Encrypted nonce | Encrypt a unique counter value with the same key | Unique — nonce must never repeat |

Both methods are acceptable per NIST. The random method is simpler and
recommended for most applications. The encrypted nonce method avoids
entropy concerns on constrained devices but requires careful counter
management to ensure the nonce never repeats.

**Practical takeaway for payment code:** use `SecureRandom` to generate a
fresh IV for every encryption call. It is simpler, less error-prone, and
sufficient for all payment terminal use cases.

## IV size reference

| Algorithm | Mode | Required IV size |
|---|---|---|
| 3DES (DESede) | CBC | 8 bytes |
| AES | CBC | 16 bytes |
| AES | GCM | 12 bytes (96 bits) — recommended |
| DES | CBC | 8 bytes |

**Note on AES/GCM:** GCM uses a nonce instead of an IV. The same rule applies —
the nonce must be unique for every encryption operation with the same key.
Nonce reuse in GCM is even more catastrophic than IV reuse in CBC because
it also leaks the authentication key.

## Detection difficulty for SAST tools

| Pattern | Regex detects? | LLM detects? | Why |
|---|---|---|---|
| `new byte[16]` as IV | Partial | Yes | Regex flags all byte arrays, LLM understands context |
| Hardcoded IV string | Yes | Yes | Direct string match |
| IV generated once, used in loop | No | Yes | Needs control flow understanding |
| IV stored as class field and reused | No | Yes | Needs scope and lifecycle analysis |
| Kotlin `by lazy` IV | No | Yes | Needs understanding of lazy initialization semantics |
| Correct `SecureRandom` IV | N/A | Yes | LLM confirms safe — no false positive |

---

## Why an LLM detects this better than regex

A regex tool can flag `new byte[16]` but cannot reason about:

- Whether that byte array is being used as an IV or for something else entirely
- Whether an IV variable is generated once at class instantiation and reused
  across method calls — the most dangerous pattern in production code
- Whether `SecureRandom` is actually used to fill the IV properly
- The difference between `new byte[8]` used as an IV for 3DES (critical)
  versus `new byte[8]` used as a read buffer (safe)
- Kotlin's `by lazy` pattern where the IV is initialized once and cached
  for the lifetime of the object

An LLM reads the variable name, how it is initialized, where it is passed,
and whether it is regenerated on each encryption call.

## Vulnerable patterns — Java

```java
// Pattern 1 — zero IV (most common mistake)
IvParameterSpec iv = new IvParameterSpec(new byte[16]); // AES-CBC
IvParameterSpec iv = new IvParameterSpec(new byte[8]);  // 3DES-CBC

// Pattern 2 — hardcoded IV as byte array
byte[] ivBytes = {0x01, 0x02, 0x03, 0x04, 0x05, 0x06, 0x07, 0x08,
                  0x09, 0x0A, 0x0B, 0x0C, 0x0D, 0x0E, 0x0F, 0x10};
IvParameterSpec iv = new IvParameterSpec(ivBytes);

// Pattern 3 — hardcoded IV as string bytes
IvParameterSpec iv = new IvParameterSpec("1234567890123456".getBytes());

// Pattern 4 — IV stored as static field and reused across all encryptions
// This is the most dangerous production pattern — looks legitimate at first glance
public class PaymentEncryptor {
    private static final IvParameterSpec IV =
        new IvParameterSpec(new byte[8]); // Created once, reused forever

    public byte[] encrypt(byte[] data) {
        Cipher cipher = Cipher.getInstance("DESede/CBC/PKCS5Padding");
        cipher.init(Cipher.ENCRYPT_MODE, key, IV); // Same IV every call
        return cipher.doFinal(data);
    }
}

// Pattern 5 — real company scenario: 3DES bank communication with fixed IV
// An attacker observing network traffic can detect repeated transaction amounts
public class BankMessageEncryptor {
    private static final byte[] FIXED_IV = new byte[8]; // ALL ZEROS

    public byte[] encryptTransaction(Transaction tx) {
        Cipher cipher = Cipher.getInstance("DESede/CBC/PKCS5Padding");
        IvParameterSpec ivSpec = new IvParameterSpec(FIXED_IV);
        cipher.init(Cipher.ENCRYPT_MODE, bankKey, ivSpec);
        // Same IV for every transaction — patterns become visible over time
        return cipher.doFinal(tx.toBytes());
    }
}
```

## Vulnerable patterns — Kotlin

```kotlin
// Pattern 1 — zero IV
val iv = IvParameterSpec(ByteArray(16)) // AES-CBC
val iv = IvParameterSpec(ByteArray(8))  // 3DES-CBC

// Pattern 2 — hardcoded IV
val iv = IvParameterSpec("1234567890123456".toByteArray())

// Pattern 3 — companion object IV (reused across all instances)
class PaymentEncryptor {
    companion object {
        private val IV = IvParameterSpec(ByteArray(8)) // Shared, reused forever
    }

    fun encrypt(data: ByteArray): ByteArray {
        val cipher = Cipher.getInstance("DESede/CBC/PKCS5Padding")
        cipher.init(Cipher.ENCRYPT_MODE, key, IV) // IV never changes
        return cipher.doFinal(data)
    }
}

// Pattern 4 — Kotlin lazy initialization (IV created once, reused forever)
// The `by lazy` delegate looks idiomatic but creates the same reuse problem
private val iv: IvParameterSpec by lazy {
    IvParameterSpec(ByteArray(8)) // Generated once at first access, cached forever
}

fun encrypt(data: ByteArray): ByteArray {
    cipher.init(Cipher.ENCRYPT_MODE, key, iv) // Same IV on every call
    return cipher.doFinal(data)
}
```

## False positive patterns — do not flag these

```java
// FALSE POSITIVE 1 — IV generated fresh with SecureRandom on each call
byte[] ivBytes = new byte[16];
new SecureRandom().nextBytes(ivBytes);
IvParameterSpec iv = new IvParameterSpec(ivBytes); // Safe — fresh every time

// FALSE POSITIVE 2 — IV read from received ciphertext for decryption
// Standard and correct pattern — the sender prepended the IV
byte[] ivBytes = Arrays.copyOf(ciphertext, 16);
IvParameterSpec iv = new IvParameterSpec(ivBytes); // Safe — decryption only

// FALSE POSITIVE 3 — AES/GCM with fresh nonce
byte[] nonce = new byte[12];
new SecureRandom().nextBytes(nonce);
GCMParameterSpec spec = new GCMParameterSpec(128, nonce); // Safe

// FALSE POSITIVE 4 — new byte[16] used as output buffer, not as IV
byte[] outputBuffer = new byte[16]; // Safe — not an IV
```

## Secure alternatives

```java
// For AES-CBC — generate fresh IV on every encryption call
byte[] ivBytes = new byte[16];
new SecureRandom().nextBytes(ivBytes);
IvParameterSpec iv = new IvParameterSpec(ivBytes);

Cipher cipher = Cipher.getInstance("AES/CBC/PKCS5Padding");
cipher.init(Cipher.ENCRYPT_MODE, key, iv);
byte[] ciphertext = cipher.doFinal(plaintext);

// Prepend IV to ciphertext — IV is not secret, receiver needs it to decrypt
byte[] output = new byte[ivBytes.length + ciphertext.length];
System.arraycopy(ivBytes, 0, output, 0, ivBytes.length);
System.arraycopy(ciphertext, 0, output, ivBytes.length, ciphertext.length);

// For 3DES-CBC bank communication — secure version with fresh IV per transaction
public byte[] encryptTransaction(Transaction tx) {
    byte[] ivBytes = new byte[8];
    new SecureRandom().nextBytes(ivBytes);

    Cipher cipher = Cipher.getInstance("DESede/CBC/PKCS5Padding");
    cipher.init(Cipher.ENCRYPT_MODE, bankKey, new IvParameterSpec(ivBytes));
    byte[] ciphertext = cipher.doFinal(tx.toBytes());

    // Prepend IV so the bank can extract it for decryption
    byte[] output = new byte[ivBytes.length + ciphertext.length];
    System.arraycopy(ivBytes, 0, output, 0, ivBytes.length);
    System.arraycopy(ciphertext, 0, output, ivBytes.length, ciphertext.length);
    return output;
}

// Best long-term alternative — AES/GCM provides authenticated encryption
// and nonce management with no padding oracle risk
byte[] nonce = new byte[12];
new SecureRandom().nextBytes(nonce);
GCMParameterSpec spec = new GCMParameterSpec(128, nonce);
Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
cipher.init(Cipher.ENCRYPT_MODE, key, spec);
```

Kotlin secure version:

```kotlin
// Generate fresh IV inside the function — never store as a field
fun encrypt(data: ByteArray): ByteArray {
    val ivBytes = ByteArray(8)
    SecureRandom().nextBytes(ivBytes)
    val iv = IvParameterSpec(ivBytes)

    val cipher = Cipher.getInstance("DESede/CBC/PKCS5Padding")
    cipher.init(Cipher.ENCRYPT_MODE, key, iv)
    val ciphertext = cipher.doFinal(data)

    // Prepend IV to output
    return ivBytes + ciphertext
}
```
