# CWE-330 — Use of insufficiently random values

**Severity:** HIGH  
**Frequency in Android payment code:** High  
**Languages:** Java, Kotlin  

---

## Description

Java provides two random number generators that look similar but are
fundamentally different in security properties:

- **`java.util.Random`:** fast and deterministic. Seeded with a predictable
  value (usually current time in milliseconds). Given enough output values,
  an attacker can mathematically reconstruct the internal state and predict
  all future values. Never acceptable for security purposes.

- **`java.security.SecureRandom`:** uses the operating system entropy source
  (`/dev/urandom` on Linux/Android). Cryptographically unpredictable. Always
  required for keys, IVs, tokens, salts, nonces, and session identifiers.

CWE-330 occurs when `Random`, `Math.random()`, or any non-cryptographic RNG
is used in a context where unpredictability is a security requirement.

### Why `Random` is dangerous for payment terminals

A developer building a PIN pad or transaction token generator reaches for
`new Random().nextInt(9000) + 1000` because it looks correct — it produces
a 4-digit number. But `Random` is a linear congruential generator: its entire
future output is determined by its seed. An attacker who observes a small
number of generated values can reconstruct the seed and predict every future
PIN the terminal will generate.

**Attack scenario:**
1. Attacker intercepts 3 consecutive transaction tokens from a payment terminal
2. Uses the known LCG algorithm to reconstruct the `Random` seed
3. Predicts the next 1000 PIN values the terminal will generate
4. Uses predicted PINs to authorize fraudulent transactions

This attack requires no cryptographic expertise — open-source tools automate
the seed reconstruction.

### Android-specific historical note

Before Android 4.4 (KitKat), `SecureRandom` had a known implementation bug
on some devices where it was seeded with a predictable value, effectively
making it as weak as `Random`. This affected Bitcoin wallets and payment
applications in 2013. Always use Android API level 19+ and never manually
seed `SecureRandom` — let the OS provide entropy.

## Relationship to other CWEs

CWE-330 is an abstract class-level weakness. The CWE specification marks
direct mapping to CWE-330 as DISCOURAGED — prefer the more specific child
CWEs for accurate reporting. For your Phase 3 implementation, detect these
specific children:

| CWE | Focus | Primary detection signal |
|---|---|---|
| CWE-331 — Insufficient entropy | Seed strength too weak | `new Random(System.currentTimeMillis())` |
| CWE-335 — Incorrect PRNG seeding | Manual seed override | `secureRandom.setSeed(fixedValue)` |
| CWE-338 — Use of cryptographically weak PRNG | Using Random for crypto | `Random` or `Math.random()` in payment context |

**For payment terminals:** CWE-338 is the most direct and accurate mapping
when `Random` is used instead of `SecureRandom` in security-sensitive contexts
such as PIN generation, token creation, or key derivation.

## Detection logic — context-based

`Random` is not always a vulnerability. The AI must determine whether
the random value is used in a security-sensitive context.

**Flag as CWE-330 / CWE-338 when `Random` or `Math.random()` is used for:**

| Context | Examples |
|---|---|
| PIN generation | `generatePin()`, `createPin()`, `randomPin` |
| Token generation | `sessionToken`, `authToken`, `transactionId`, `apiKey` |
| Key or IV generation | any value passed to `SecretKeySpec`, `IvParameterSpec` |
| Salt generation | any value passed to `PBEKeySpec` or used before hashing |
| Security challenge | `nonce`, `challenge`, `verificationCode`, `otp` |
| Password reset tokens | `resetToken`, `activationCode` |

**Do not flag when `Random` is used for:**
- UI animations and visual effects
- Test data generation in `@Test` methods
- Game logic and simulations
- Non-security shuffling or sampling
- Load balancing or retry jitter

## Detection difficulty for SAST tools

| Pattern | Regex detects? | LLM detects? | Why |
|---|---|---|---|
| `new Random()` in security context | Partial | Yes | Regex flags all Random, LLM checks context |
| `Math.random()` for token | No | Yes | Method name and assignment context |
| `Random` seeded with timestamp | No | Yes | Recognizes time-based seed as predictable |
| `Random` seeded with userId | No | Yes | Recognizes small seed space |
| `RandomGenerator.getDefault()` | No | Yes | Newer API, same problem |
| `Random` for PIN generation | No | Yes | Understands payment terminal context |
| `Random` for game shuffle | N/A | Yes | Correctly ignores non-security usage |
| Manual `SecureRandom.setSeed()` | No | Yes | Detects developer overriding entropy |

---

## Why an LLM detects this better than regex

A regex tool that flags every use of `Random` produces enormous numbers of
false positives — most `Random` usage in an Android codebase is legitimate.
A tool that flags only `Random` in method names containing "key" or "token"
misses cases like PIN generation where the variable is simply named `pin`.

An LLM reads the full method context, understands that a payment terminal
generating a PIN requires `SecureRandom`, and makes the correct determination
even when the variable name does not contain obvious security keywords.

## Vulnerable patterns — Java

```java
// Pattern 1 — Random for PIN generation (payment terminal specific)
// CRITICAL: attacker can predict all future PINs after observing a few
public int generatePin() {
    return new Random().nextInt(9000) + 1000; // 4-digit PIN — predictable
}

// Pattern 2 — Random for session token
String sessionToken = String.valueOf(new Random().nextLong());

// Pattern 3 — Math.random() for security value
double token = Math.random(); // Math.random() uses Random internally

// Pattern 4 — Random seeded with timestamp (CWE-331: insufficient entropy)
// Timestamp-based seed is guessable within a small time window
Random rng = new Random(System.currentTimeMillis());
byte[] key = new byte[16];
rng.nextBytes(key);

// Pattern 5 — Random seeded with small value space (CWE-331)
// userId is a 32-bit integer — only ~4 billion possible seeds
Random rng = new Random();
rng.setSeed(userId); // Predictable seed space, brute-forceable
byte[] token = new byte[32];
rng.nextBytes(token);

// Pattern 6 — Random for IV generation
Random rng = new Random();
byte[] iv = new byte[16];
rng.nextBytes(iv); // Predictable IV — compounds with CWE-329

// Pattern 7 — Random for salt generation
Random rng = new Random();
byte[] salt = new byte[16];
rng.nextBytes(salt); // Predictable salt defeats the purpose of salting

// Pattern 8 — ThreadLocalRandom (also not cryptographically secure)
byte[] token = new byte[32];
ThreadLocalRandom.current().nextBytes(token); // Still not SecureRandom

// Pattern 9 — Java 17+ RandomGenerator API (modern but still not secure)
// Developers using the new API may assume it is cryptographically safe — it is not
RandomGenerator random = RandomGenerator.getDefault();
int pin = random.nextInt(9000) + 1000; // Predictable — not SecureRandom

// Pattern 10 — Manual SecureRandom seed override (CWE-335)
// Overriding the OS entropy with a fixed seed defeats the purpose of SecureRandom
SecureRandom sr = new SecureRandom();
sr.setSeed(12345L); // Fixed seed — now behaves like a predictable RNG
byte[] key = new byte[32];
sr.nextBytes(key);
```

## Vulnerable patterns — Kotlin

```kotlin
// Pattern 1 — PIN generation with Random
fun generatePin(): Int = Random().nextInt(9000) + 1000

// Pattern 2 — Kotlin's built-in random (not cryptographically secure)
val pin = (1000..9999).random()           // Uses kotlin.random.Random — NOT secure
val token = (0..Long.MAX_VALUE).random().toString()

// Pattern 3 — Random for key bytes
val keyBytes = ByteArray(16).also { Random().nextBytes(it) }

// Pattern 4 — extension function hiding weak RNG
fun generateToken(): String =
    (1..32).map { ('a'..'z').random() }.joinToString("") // kotlin.random.Random

// Pattern 5 — seeded with timestamp
val rng = java.util.Random(System.currentTimeMillis())
val token = rng.nextLong().toString() // Predictable
```

## False positive patterns — do not flag these

```java
// FALSE POSITIVE 1 — Random for UI animation timing
int delay = new Random().nextInt(500); // Safe — no security requirement

// FALSE POSITIVE 2 — Random for test data generation
@Test
public void testPaymentFlow() {
    int testAmount = new Random().nextInt(10000); // Safe — test context
}

// FALSE POSITIVE 3 — Random for retry jitter in network code
int jitter = new Random().nextInt(1000); // Safe — timing, not security

// FALSE POSITIVE 4 — Random for game or simulation
int roll = new Random().nextInt(6) + 1; // Safe — dice roll

// FALSE POSITIVE 5 — SecureRandom used correctly
byte[] token = new byte[32];
new SecureRandom().nextBytes(token); // Safe — correct RNG
```

```kotlin
// FALSE POSITIVE 6 — Kotlin random for non-security shuffle
val shuffled = listOf(1, 2, 3, 4, 5).shuffled() // Safe — not security-sensitive
```

## Secure alternatives

```java
// Always use SecureRandom for any security-sensitive random value

// Secure PIN generation for payment terminals
public int generatePin() {
    return new SecureRandom().nextInt(9000) + 1000;
}

// Secure session token
byte[] tokenBytes = new byte[32];
new SecureRandom().nextBytes(tokenBytes);
String sessionToken = Base64.getUrlEncoder()
                            .withoutPadding()
                            .encodeToString(tokenBytes);

// Secure key generation
byte[] keyBytes = new byte[32]; // 256-bit key
new SecureRandom().nextBytes(keyBytes);
SecretKeySpec key = new SecretKeySpec(keyBytes, "AES");

// Secure IV generation
byte[] ivBytes = new byte[16];
new SecureRandom().nextBytes(ivBytes);
IvParameterSpec iv = new IvParameterSpec(ivBytes);

// Secure salt generation
byte[] salt = new byte[16];
new SecureRandom().nextBytes(salt);

// Java 17+ secure alternative — use SecureRandom explicitly, not getDefault()
SecureRandom secure = new SecureRandom();
int pin = secure.nextInt(9000) + 1000; // Safe
```

```kotlin
// Kotlin secure alternatives
import java.security.SecureRandom

// Secure PIN
fun generatePin(): Int = SecureRandom().nextInt(9000) + 1000

// Secure token
fun generateToken(): String {
    val bytes = ByteArray(32)
    SecureRandom().nextBytes(bytes)
    return Base64.getUrlEncoder().withoutPadding().encodeToString(bytes)
}

// Secure random bytes extension
fun secureRandomBytes(size: Int): ByteArray =
    ByteArray(size).also { SecureRandom().nextBytes(it) }
```
