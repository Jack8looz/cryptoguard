# CWE-798 — Use of hardcoded credentials or cryptographic keys

**Severity:** CRITICAL  
**Frequency in Android payment code:** Very high  
**Languages:** Java, Kotlin  

---

## Description

A hardcoded credential or cryptographic key is any secret value written directly
in source code as a string literal, byte array, constant, or resource file. This
is critical because source code is never truly private:

- **Source control:** Git history preserves every commit forever. A key committed
  and later deleted is still recoverable with `git log`.
- **Compiled APKs:** Android APKs can be decompiled in seconds using tools like
  `jadx` or `apktool`. String literals in Java/Kotlin survive compilation and
  are directly visible in decompiled code.
- **Memory dumps:** Keys loaded into memory can be extracted from process memory
  dumps during runtime analysis.
- **Logs and error messages:** Hardcoded secrets frequently appear in stack traces
  and debug logs.

For a payment terminal application, a hardcoded 3DES or RSA key means any attacker
with access to the APK can extract the key and decrypt all communication.

### Attack scenario — why "private repository" is not a solution

Even with a private repository, hardcoded credentials remain at risk:

1. Developer commits an encryption key to a private GitHub repository
2. Months later, the developer leaves the company — they still have a local clone
3. Or: CI/CD pipeline logs capture the key value in build output
4. Or: a junior developer shares their screen during a debugging session
5. Or: the repository is accidentally made public for 30 seconds during a settings change

**Result:** the key is compromised even though the repository was always intended
to be private. The only safe approach is to never put secrets in source code at all.

## Detection difficulty for SAST tools

| Pattern | Regex detects? | LLM detects? | Why |
|---|---|---|---|
| `key = "abc123"` | Yes | Yes | Simple string literal |
| `byte[]{0x41, 0x42, ...}` | No | Yes | Needs semantic understanding |
| `"sec" + "ret"` | No | Yes | String built by concatenation |
| `getString(R.string.hidden_key)` | No | Yes | Cross-file reference |
| KeyStore alias vs key value | No | Yes | Context distinction |
| `const val API_SECRET = "..."` | Partial | Yes | Kotlin compile-time inlining |
| `if (BuildConfig.DEBUG) key = "test"` | No | Yes | Conditional context |

**CryptoGuard advantage:** an LLM understands that `keyAlias` is not a secret
even though it contains the word "key", and that a `const val` is more dangerous
than a regular variable because Kotlin inlines it at every call site.

---

## Why an LLM detects this better than regex

A regex tool searching for quoted strings near "key" or "password" cannot reason about:

- A key stored as a byte array: `byte[] key = {0x41, 0x42, 0x43, ...}`
- A key built by concatenation: `String k = "secret" + "key123"`
- Context difference: `String keyAlias = "my_key"` is a KeyStore alias (safe)
  versus `new SecretKeySpec("hardcoded".getBytes(), "AES")` (critical)
- Whether a string is actually a secret or just a configuration label
- A resource reference: `getString(R.string.api_key)` where the actual value
  is hardcoded in `res/values/strings.xml`
- Debug-only keys that should generate a warning but not a critical flag

An LLM understands the difference between a key alias, a key ID, and an actual
key value — and adjusts severity based on context.

## Vulnerable patterns — Java

```java
// Pattern 1 — hardcoded AES key as string
SecretKeySpec key = new SecretKeySpec("hardcoded_key_123".getBytes(), "AES");

// Pattern 2 — hardcoded key as byte array
private static final byte[] KEY = {
    0x41, 0x42, 0x43, 0x44, 0x45, 0x46, 0x47, 0x48,
    0x49, 0x4A, 0x4B, 0x4C, 0x4D, 0x4E, 0x4F, 0x50
};

// Pattern 3 — hardcoded password
String password = "admin123";
String dbPassword = "P@ssw0rd!";

// Pattern 4 — hardcoded RSA private key
String privateKey = "-----BEGIN PRIVATE KEY-----\nMIIEvQIBADANBg...";

// Pattern 5 — hardcoded API token
String apiToken = "Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...";

// Pattern 6 — payment terminal specific: hardcoded PIN encryption key
// EXTREMELY COMMON in payment code
private static final String PIN_KEY = "0123456789ABCDEF"; // 16-byte 3DES key
// Any attacker with the APK can decrypt all PIN blocks using this key

// Pattern 7 — hardcoded Kerberos key
KerberosKey key = new KerberosKey(principal, "hardcoded_secret".getBytes(), 17);
```

## Vulnerable patterns — Kotlin

```kotlin
// Pattern 1 — regular variable
val key = SecretKeySpec("hardcoded_key_123".toByteArray(), "AES")
private val SECRET = "my_super_secret_key"
val password = "admin123"

// Pattern 2 — const val is WORSE than Java static final
// Kotlin inlines const val at every call site during compilation,
// making it visible in more locations in the decompiled bytecode
const val API_SECRET = "sk_test_123456789"
const val ENCRYPTION_KEY = "payment_master_key_2024"

// Pattern 3 — data class with hardcoded default value (easy to miss)
data class PaymentConfig(
    val apiKey: String = "default_key_123",
    val terminalSecret: String = "terminal_secret_abc"
)
```

## False positive patterns — do not flag these

These patterns look like hardcoded credentials but are not vulnerabilities.
The AI must distinguish them from real secrets:

```java
// FALSE POSITIVE 1 — KeyStore alias (this is a label, not the key itself)
String keyAlias = "payment_encryption_key_2024";
KeyStore.getInstance("AndroidKeyStore").getKey(keyAlias, null); // SAFE

// FALSE POSITIVE 2 — AWS KMS key ID (this is a reference, not the key)
String keyId = "arn:aws:kms:us-east-1:123456789:key/abcd1234"; // SAFE

// FALSE POSITIVE 3 — debug/test key inside a BuildConfig.DEBUG block
// Flag as WARNING only, not CRITICAL — must not reach production
if (BuildConfig.DEBUG) {
    String testKey = "test_key_123"; // WARNING — not CRITICAL
}

// FALSE POSITIVE 4 — configuration label, not a secret value
String keyName = "RSA_PUBLIC_KEY_ALIAS"; // SAFE — just a name

// FALSE POSITIVE 5 — public key (public keys are not secrets)
String publicKey = "-----BEGIN PUBLIC KEY-----\nMIIBIjANBgkq..."; // SAFE

// FALSE POSITIVE 6 — KerberosKey derived from user input or method parameter
byte[] keyData = readLine().getBytes();
KerberosKey key = new KerberosKey(principal, keyData, 17); // NOT hardcoded — SAFE
```

## Secure alternatives

```java
// Option 1 — Android KeyStore (recommended for Android payment apps)
// Keys are stored in hardware-backed secure storage on the device
KeyStore keyStore = KeyStore.getInstance("AndroidKeyStore");
keyStore.load(null);
SecretKey key = (SecretKey) keyStore.getKey("my_key_alias", null);

// Option 2 — environment variable (for backend services)
String keyValue = System.getenv("ENCRYPTION_KEY");
SecretKeySpec key = new SecretKeySpec(
    Base64.getDecoder().decode(keyValue), "AES"
);

// Option 3 — generate a new key securely at runtime
// Use when you do not need to persist the key across sessions
KeyGenerator keyGen = KeyGenerator.getInstance("AES");
keyGen.init(256, new SecureRandom());
SecretKey key = keyGen.generateKey();

// Option 4 — Hardware Security Module (HSM) binding
// For payment terminals: store the key in the secure element,
// never in application code. The key never leaves the hardware.
SecureElement se = SecureElement.getInstance();
SecretKey key = se.getKey("payment_master_key");
```
