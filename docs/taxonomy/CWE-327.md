# CWE-327 — Use of a broken or risky cryptographic algorithm

**Severity:** CRITICAL  
**Frequency in Android payment code:** Very high  
**Languages:** Java, Kotlin  

---

## Description

A cryptographic algorithm is considered broken when mathematical attacks exist that
allow an attacker to recover plaintext, forge signatures, or find collisions without
needing the secret key. It is considered risky when its key size is too short to
resist brute-force attacks with modern hardware.

Specific reasons per algorithm:

- **MD5:** collision attacks are publicly known and trivially executable. Two different
  inputs can be crafted to produce the same hash. Broken since 2004.

- **SHA-1:** collision attacks demonstrated by Google's SHAttered attack in 2017.
  SHA-1 deprecation timeline:
  - 2011: NIST formally deprecated SHA-1 for digital signatures
  - 2017: SHAttered attack demonstrated the first practical collision
  - 2022: Chrome and Firefox removed SHA-1 certificate support
  - 2025: Must never be used for any security purpose

- **DES:** 56-bit key. Brute-forceable in under 24 hours with commodity hardware.
  Retired by NIST in 2005.

- **3DES (Triple DES / DESede):** 112-bit effective security. Vulnerable to the
  Sweet32 birthday attack on long-lived sessions. Deprecated by NIST in 2023.
  Acceptable ONLY in legacy bank protocol communication where the bank mandates
  it — must not be used anywhere else in the codebase.

- **RC4:** statistical biases in the keystream allow plaintext recovery.
  Prohibited by RFC 7465.

- **AES/ECB:** not a broken algorithm but a broken mode. ECB encrypts identical
  plaintext blocks to identical ciphertext blocks, leaking data patterns visibly.
  On Android, calling `Cipher.getInstance("AES")` without specifying a mode
  historically defaults to AES/ECB/PKCS5Padding on many providers — making
  unqualified "AES" usage as dangerous as explicitly specifying ECB.

## Detection difficulty for SAST tools

| Pattern | Regex detects? | LLM detects? | Why |
|---|---|---|---|
| `getInstance("MD5")` | Yes | Yes | Simple string match |
| `getInstance("AES")` no mode | Partial | Yes | Needs knowledge of Android default behavior |
| 3DES in bank class vs login class | No | Yes | Context and class name reasoning |
| MD5 for file checksum vs password | No | Yes | Intent understanding |
| Extension function hiding MD5 | No | Yes | Indirect call tracing |
| Test class vs production class | No | Yes | Annotation and class context |

**CryptoGuard advantage:** an LLM recognizes that `Cipher.getInstance("AES")`
on Android is equivalent to `Cipher.getInstance("AES/ECB/PKCS5Padding")` and
flags it accordingly, while also understanding that the same MD5 call is
acceptable for a file deduplication checksum but critical for a password hash.

---

## Why an LLM detects this better than regex

A regex tool can flag the string "DES" or "MD5" but cannot distinguish:

- `MessageDigest.getInstance("MD5")` used for a security-sensitive password hash
  (CRITICAL) versus used for a non-security file deduplication checksum (acceptable)
- `Cipher.getInstance("AES/ECB/PKCS5Padding")` (CRITICAL) versus
  `Cipher.getInstance("AES/GCM/NoPadding")` (secure)
- `Cipher.getInstance("AES")` on Android — looks safe but defaults to ECB (CRITICAL)
- 3DES used in a class named `BankProtocolHandler` (WARNING — legacy compliance)
  versus used in a class named `LoginManager` (CRITICAL — no justification)
- MD5 inside a `@Test` annotated method (lower severity) versus in production code
- An extension function like `fun String.md5()` that hides the broken algorithm
  behind a clean-looking API call

An LLM reads the surrounding code, class name, annotations, and imports to
reason about intent and severity.

## Vulnerable patterns — Java

```java
// Pattern 1 — broken hash algorithm
MessageDigest md = MessageDigest.getInstance("MD5");
MessageDigest md = MessageDigest.getInstance("SHA-1");

// Pattern 2 — broken symmetric encryption
Cipher des = Cipher.getInstance("DES/CBC/PKCS5Padding");
Cipher des = Cipher.getInstance("DESede/CBC/PKCS5Padding"); // 3DES

// Pattern 3 — broken mode (ECB)
Cipher cipher = Cipher.getInstance("AES/ECB/PKCS5Padding");

// Pattern 4 — broken stream cipher
Cipher rc4 = Cipher.getInstance("RC4");

// Pattern 5 — no mode specified (Android defaults to ECB — equally dangerous)
Cipher cipher = Cipher.getInstance("AES");
// On Android, this is equivalent to AES/ECB/PKCS5Padding on many providers
// Developers often believe this is safe — it is not

// Pattern 6 — no padding specified with AES
Cipher cipher = Cipher.getInstance("AES/CBC");
// Missing padding specification can trigger provider-dependent insecure defaults
```

## Vulnerable patterns — Kotlin

```kotlin
// Direct usage
val md = MessageDigest.getInstance("MD5")
val cipher = Cipher.getInstance("AES/ECB/PKCS5Padding")
val des = Cipher.getInstance("DES/CBC/PKCS5Padding")

// AES without mode — especially dangerous on Android
val cipher = Cipher.getInstance("AES")

// Extension function hiding the broken algorithm (harder to detect)
// The function definition is the vulnerability — not the call site
fun String.md5(): String =
    MessageDigest.getInstance("MD5")
        .digest(toByteArray())
        .joinToString("") { "%02x".format(it) }

// Usage of the extension looks innocent but is still vulnerable
val hash = password.md5()  // CWE-327 — MD5 used via extension function
```

## False positive patterns — do not flag these

These patterns involve broken algorithms but are not security vulnerabilities
in context. The AI must distinguish them by reading surrounding code:

```java
// FALSE POSITIVE 1 — MD5 for non-security file deduplication checksum
// Context: no security guarantee required, just duplicate detection
String fileChecksum = DigestUtils.md5Hex(inputStream); // Acceptable

// FALSE POSITIVE 2 — 3DES in a legacy bank protocol handler
// Context: bank mandate, no alternative available
// Flag as WARNING only — not CRITICAL
if (legacyBankSystem.isConnected()) {
    Cipher cipher = Cipher.getInstance("DESede/CBC/PKCS5Padding"); // WARNING
}

// FALSE POSITIVE 3 — broken algorithm in a test class
// Context: @Test annotation, test file path, or test class name
@Test
public void testLegacyHashFunction() {
    MessageDigest md = MessageDigest.getInstance("MD5"); // WARNING — not CRITICAL
    // Flagged at lower severity: test code, but should still be cleaned up
}

// FALSE POSITIVE 4 — SHA-1 for Git-style content addressing (non-security use)
// Context: no cryptographic security guarantee required
MessageDigest sha1 = MessageDigest.getInstance("SHA-1"); // Acceptable for content ID
```

## Secure alternatives

```java
// Secure hash — general purpose
MessageDigest md = MessageDigest.getInstance("SHA-256");
MessageDigest md = MessageDigest.getInstance("SHA-3-256");

// Secure symmetric encryption — authenticated encryption with GCM
// GCM provides both confidentiality and integrity in one operation
Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");

// Always specify the full transformation string — never use "AES" alone
// WRONG: Cipher.getInstance("AES")
// RIGHT: Cipher.getInstance("AES/GCM/NoPadding")
```
