# CWE-328 — Use of weak hash — missing or inadequate salt

**Severity:** HIGH  
**Frequency in Android payment code:** Medium  
**Languages:** Java, Kotlin  

> **Historical note:** This entry was previously named "Reversible One-Way Hash"
> before the CWE catalogue was updated in 2021. If you encounter this older name
> in legacy documentation or audit reports, it refers to this same weakness.

---

## Description

A salt is a random value generated uniquely for each password and combined
with it before hashing. Its purpose is to ensure that:

1. Two users with the same password produce different hash values
2. Precomputed rainbow tables are rendered useless
3. An attacker who obtains the hash database must crack each hash
   individually rather than the entire database at once

CWE-328 occurs when a hash is computed with no salt, a static salt, a
predictable salt, or a salt that is too short to be effective.

### Why salt defeats rainbow tables

A rainbow table is a precomputed lookup table mapping hash values back to
their original passwords. A single rainbow table for MD5 covering all
8-character alphanumeric passwords requires hundreds of gigabytes of storage
and can crack any unsalted MD5 hash in seconds by simple lookup.

**Without salt:** one rainbow table cracks every password in the database
simultaneously. An attacker downloads a prebuilt table and looks up each
hash directly.

**With a unique per-user salt:** the attacker must build a completely separate
rainbow table for each unique salt value. With a 128-bit random salt (2^128
possible values), constructing rainbow tables for all possible salts is
physically impossible — it would require more storage than exists on Earth.
The attacker is forced to crack each password hash individually using
brute-force, which is orders of magnitude slower.

**Practical impact for payment terminals:** if a user database is leaked and
passwords were stored without salts, every password in the database can be
cracked in minutes using freely available tools like hashcat and prebuilt
rainbow tables. With proper salting, cracking a single password takes hours
to days depending on its strength.

### Why salting matters even with slow algorithms

CWE-328 and CWE-916 are related but distinct:
- **CWE-916:** wrong algorithm — using SHA-256 instead of bcrypt
- **CWE-328:** wrong salting — using bcrypt but with a reused or
  predictable salt

A developer using bcrypt but hardcoding the same salt for every user
still has a vulnerability — identical passwords still produce identical
hashes, and a rainbow table attack becomes feasible again for that
fixed salt value.

### Note on bcrypt and Argon2

bcrypt and Argon2 handle salting internally and automatically — they
generate a fresh random salt on every call and embed it in the output
string. A developer who calls `BCrypt.hashpw(password, BCrypt.gensalt())`
correctly has no CWE-328 issue.

CWE-328 primarily affects code using raw `MessageDigest`, `PBKDF2`,
or `scrypt` where the developer is responsible for salt generation.

### Note on OT and firmware code

The CWE specification cites the OT:ICEFALL research (2022) as a related
example, where industrial control system firmware used only 32 bits of a
512-bit secret for JTAG access control — a form of insufficient input
entropy in a hash-based authentication scheme. While not directly relevant
to Android payment code, this pattern may appear in payment terminal
firmware layers: hash-based authentication using a truncated or predictable
input. Flag any hash-based access control that derives its input from a
value shorter than 128 bits.

## Detection logic — what to flag

**Flag as CWE-328 when:**
- A password is hashed with `MessageDigest` and no salt is present
- PBKDF2 is called with a static, hardcoded, or predictable salt
- The salt is derived from a predictable value such as username, email,
  user ID, or timestamp
- The salt is shorter than 16 bytes (128 bits)
- The same salt constant is reused across multiple hash operations

**Do not flag when:**
- bcrypt is used with `BCrypt.gensalt()` — salt is handled internally
- Argon2 is used — salt is handled internally
- PBKDF2 is called with a fresh `SecureRandom` salt of 16+ bytes
- SHA-256 is used for non-password purposes such as file hash or HMAC

## Detection difficulty for SAST tools

| Pattern | Regex detects? | LLM detects? | Why |
|---|---|---|---|
| SHA-256 with no salt on password | No | Yes | Must recognize absent salt as vulnerability |
| PBKDF2 with hardcoded salt | Partial | Yes | Must recognize salt value as static |
| Salt derived from username | No | Yes | Must understand predictability of input |
| bcrypt with gensalt() | N/A | Yes | Correctly identifies as safe |
| Salt shorter than 16 bytes | No | Yes | Must evaluate salt byte array length |
| Same salt constant reused | No | Yes | Must trace salt usage across calls |

## Why an LLM detects this better than regex

The hardest case is the absent salt — there is no string to match because
the salt is simply missing. An LLM reading:

```java
byte[] hash = MessageDigest.getInstance("SHA-256").digest(password.getBytes());
```

understands that no salt is present and flags it. A regex tool has nothing
to match against.

The second hard case is a predictable salt:

```java
byte[] salt = username.getBytes(); // Predictable — defeats salting purpose
```

An LLM understands that using the username as a salt is a vulnerability
because usernames are known to attackers. A regex tool cannot reason about
the predictability of a value.

## Vulnerable patterns — Java

```java
// Pattern 1 — no salt at all (most common)
byte[] hash = MessageDigest.getInstance("SHA-256")
                           .digest(password.getBytes());

// Pattern 2 — static hardcoded salt (same for all users)
byte[] salt = "static_salt_value".getBytes();
MessageDigest md = MessageDigest.getInstance("SHA-256");
md.update(salt);
byte[] hash = md.digest(password.getBytes());

// Pattern 3 — predictable salt derived from username
byte[] salt = username.getBytes(); // Attacker knows the username
MessageDigest md = MessageDigest.getInstance("SHA-256");
md.update(salt);
byte[] hash = md.digest(password.getBytes());

// Pattern 4 — salt derived from user ID (small predictable space)
byte[] salt = String.valueOf(userId).getBytes();
MessageDigest md = MessageDigest.getInstance("SHA-256");
md.update(salt);
byte[] hash = md.digest(password.getBytes());

// Pattern 5 — PBKDF2 with hardcoded salt
SecretKeyFactory skf = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256");
byte[] salt = "hardcoded_salt".getBytes(); // Same for all users
PBEKeySpec spec = new PBEKeySpec(password.toCharArray(), salt, 310000, 256);

// Pattern 6 — salt too short (less than 16 bytes)
byte[] salt = new byte[4]; // Only 32 bits — insufficient
new SecureRandom().nextBytes(salt);
PBEKeySpec spec = new PBEKeySpec(password.toCharArray(), salt, 310000, 256);

// Pattern 7 — salt reused across sessions (stored as static constant)
// Generated once at class load — same salt for every user
private static final byte[] SALT = new byte[16];
static {
    new SecureRandom().nextBytes(SALT);
}
PBEKeySpec spec = new PBEKeySpec(password.toCharArray(), SALT, 310000, 256);
```

## Vulnerable patterns — Kotlin

```kotlin
// Pattern 1 — no salt
val hash = MessageDigest.getInstance("SHA-256")
    .digest(password.toByteArray())

// Pattern 2 — static hardcoded salt
val salt = "static_salt".toByteArray()
val md = MessageDigest.getInstance("SHA-256")
md.update(salt)
val hash = md.digest(password.toByteArray())

// Pattern 3 — predictable salt from username
val salt = username.toByteArray() // Predictable
val md = MessageDigest.getInstance("SHA-256")
md.update(salt)
val hash = md.digest(password.toByteArray())

// Pattern 4 — PBKDF2 with hardcoded salt
val salt = "fixed_salt_123".toByteArray()
val spec = PBEKeySpec(password.toCharArray(), salt, 310000, 256)
```

## False positive patterns — do not flag these

```java
// FALSE POSITIVE 1 — bcrypt with gensalt() — salt handled internally
String hashed = BCrypt.hashpw(password, BCrypt.gensalt(12)); // Safe

// FALSE POSITIVE 2 — Argon2 — salt handled internally
Argon2 argon2 = Argon2Factory.create();
String hash = argon2.hash(3, 65536, 1, password.toCharArray()); // Safe

// FALSE POSITIVE 3 — PBKDF2 with fresh SecureRandom salt of correct length
byte[] salt = new byte[16]; // 128-bit salt — acceptable minimum
new SecureRandom().nextBytes(salt);
PBEKeySpec spec = new PBEKeySpec(
    password.toCharArray(), salt, 310000, 256); // Safe

// FALSE POSITIVE 4 — SHA-256 for non-password hashing
byte[] fileHash = MessageDigest.getInstance("SHA-256")
                               .digest(fileBytes); // Safe — not a password

// FALSE POSITIVE 5 — HMAC-SHA256 for message authentication
Mac mac = Mac.getInstance("HmacSHA256");
mac.init(secretKey);
byte[] hmac = mac.doFinal(message); // Safe — not password hashing
```

## Secure alternatives

```java
// Option 1 — bcrypt (salt handled automatically — recommended)
String hashed = BCrypt.hashpw(password, BCrypt.gensalt(12));
boolean valid = BCrypt.checkpw(password, hashed);

// Option 2 — Argon2 (salt handled automatically — OWASP #1)
Argon2 argon2 = Argon2Factory.create();
String hash = argon2.hash(3, 65536, 1, password.toCharArray());
boolean valid = argon2.verify(hash, password.toCharArray());

// Option 3 — PBKDF2 with proper random salt
// Developer is responsible for salt — must generate, store, and retrieve it
byte[] salt = new byte[16]; // 128-bit minimum, 256-bit recommended
new SecureRandom().nextBytes(salt);
SecretKeyFactory skf = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256");
PBEKeySpec spec = new PBEKeySpec(
    password.toCharArray(),
    salt,
    310000,  // OWASP 2023 minimum
    256
);
byte[] hash = skf.generateSecret(spec).getEncoded();
spec.clearPassword(); // Always clear after use
// Important: store the salt alongside the hash — it is needed for verification
```

```kotlin
// Kotlin — PBKDF2 with proper salt
val salt = ByteArray(16).also { SecureRandom().nextBytes(it) }
val spec = PBEKeySpec(password.toCharArray(), salt, 310000, 256)
val hash = SecretKeyFactory
    .getInstance("PBKDF2WithHmacSHA256")
    .generateSecret(spec)
    .encoded
spec.clearPassword()
// Store salt alongside hash for later verification
```
