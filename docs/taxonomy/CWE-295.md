# CWE-295 — Improper certificate validation

**Severity:** CRITICAL  
**Frequency in Android payment code:** Medium  
**Languages:** Java, Kotlin  

---

## Description

TLS only protects data in transit if both sides of the connection verify who
they are talking to. Certificate validation is the mechanism that does this:
the client checks that the server's certificate is signed by a trusted
Certificate Authority, and that the certificate's hostname matches the server
it is actually connecting to. CWE-295 occurs when either check is disabled,
weakened, or bypassed — the TLS handshake still completes and the connection
still shows as "encrypted," but there is no longer any guarantee about who is
on the other end.

The most common cause is a custom `TrustManager` or `HostnameVerifier`
written during development to work around a self-signed certificate or a
local test server, and then never removed before release.

### Why this is worse than no encryption at all

An unencrypted HTTP connection is at least visibly insecure — a URL starting
with `http://` is a clear signal. A TLS connection with certificate
validation disabled *looks* secure (the padlock icon shows, the connection
succeeds, the URL is `https://`) while providing none of the protection TLS
is supposed to guarantee. This makes it invisible to end users and to anyone
reviewing network traffic superficially, and it silently defeats a man-in-
the-middle attack protection that the rest of the system may be relying on.

### Attack scenario — payment terminal on public or hostile networks

1. A payment terminal disables hostname verification "temporarily" to reach
   a test backend during development.
2. The code ships to production unchanged.
3. An attacker on the same network (public Wi-Fi, a compromised router, an
   ARP-spoofing attack on a local network) presents any certificate — even
   a self-signed one issued for a completely different domain.
4. The terminal accepts it, establishes what it believes is a secure
   channel, and transmits transaction data, PINs, or authentication tokens
   directly to the attacker.

**Result:** every security property TLS was supposed to provide (server
authenticity, protection from interception) is gone, while every visible
signal still says the connection is secure.

### Direct PCI SSF relevance

PCI SSF Control Objective 6.2.d requires that transport-layer encryption
"enforce a secure version of the protocol with end-point authentication
prior to transmission" — end-point authentication is exactly what
certificate and hostname validation provide. An assessor who finds a
trust-all `TrustManager` or a `HostnameVerifier` that always returns `true`
treats it as a direct failure of 6.2.d, independent of which TLS version or
cipher suite is negotiated.

## Detection logic

**Flag when:**
- A `checkServerTrusted()` or `checkClientTrusted()` method body is empty, or
  contains no statement capable of throwing `CertificateException`
- A `HostnameVerifier.verify()` implementation (Java) or `hostnameVerifier`
  lambda (Kotlin/OkHttp) unconditionally returns `true` without comparing
  `hostname` against the session's actual peer
- `ALLOW_ALL_HOSTNAME_VERIFIER` or an equivalent deprecated permissive
  constant is used
- `onReceivedSslError()` in a `WebViewClient` calls `handler.proceed()`
  instead of `handler.cancel()`

**Do NOT flag:**
- A custom `TrustManager`/`HostnameVerifier` that contains real comparison
  logic and throws/returns `false` on mismatch (certificate pinning) — this
  satisfies PCI 6.2.d, it does not violate it
- `CertificatePinner` usage (OkHttp) — this is the recommended secure
  alternative, never the vulnerability
- The default `TrustManagerFactory`/`HostnameVerifier` obtained from the
  platform and left unmodified

**The only false positive risk:** a trust-all pattern gated behind
`BuildConfig.DEBUG` or an equivalent build flag. Flag these as WARNING
rather than CRITICAL — acceptable only for local development against a
self-signed test server, and only if there is no path for the flag to be
true in a release build.

## Detection difficulty for SAST tools

| Pattern | Regex detects? | LLM detects? | Why |
|---|---|---|---|
| Empty `checkServerTrusted()` body | Partial | Yes | Must confirm the method body has no validation logic, not just that the method exists |
| `HostnameVerifier` returning `true` unconditionally | No | Yes | Must trace the return value of a lambda/anonymous class |
| `ALLOW_ALL_HOSTNAME_VERIFIER` | Yes | Yes | Deprecated constant, safe for regex too |
| Custom `TrustManager` that legitimately validates a pinned cert | No | Yes | Must distinguish "does nothing" from "does something different but correct" |
| `WebView.onReceivedSslError()` calling `handler.proceed()` | No | Yes | Requires understanding the WebView SSL error callback contract |
| OkHttp `.hostnameVerifier { _, _ -> true }` | No | Yes | Kotlin trailing lambda, no fixed string to match |
| `SSLContext.init(null, trustAllCerts, ...)` | Partial | Yes | Must trace that `trustAllCerts` is the no-op array defined above |

**CryptoGuard advantage:** the vulnerable and secure versions of a
`TrustManager` are structurally identical — same interface, same method
signatures, same imports. The only difference is what happens *inside* the
method body, which is exactly the kind of semantic distinction regex cannot
make and an LLM can.

## Vulnerable patterns — Java

```java
// Pattern 1 — classic trust-all TrustManager
TrustManager[] trustAllCerts = new TrustManager[] {
    new X509TrustManager() {
        public X509Certificate[] getAcceptedIssuers() { return new X509Certificate[0]; }
        public void checkClientTrusted(X509Certificate[] certs, String authType) {}
        public void checkServerTrusted(X509Certificate[] certs, String authType) {} // VULNERABLE — no exception thrown, no checks performed
    }
};
SSLContext sc = SSLContext.getInstance("TLS");
sc.init(null, trustAllCerts, new SecureRandom());
HttpsURLConnection.setDefaultSSLSocketFactory(sc.getSocketFactory());

// Pattern 2 — hostname verification disabled
HttpsURLConnection.setDefaultHostnameVerifier(new HostnameVerifier() {
    public boolean verify(String hostname, SSLSession session) {
        return true; // VULNERABLE — accepts any hostname
    }
});

// Pattern 3 — deprecated ALLOW_ALL constant
HttpsURLConnection conn = (HttpsURLConnection) url.openConnection();
conn.setHostnameVerifier(org.apache.http.conn.ssl.SSLSocketFactory.ALLOW_ALL_HOSTNAME_VERIFIER); // VULNERABLE

// Pattern 4 — WebView ignoring SSL errors
webView.setWebViewClient(new WebViewClient() {
    @Override
    public void onReceivedSslError(WebView view, SslErrorHandler handler, SslError error) {
        handler.proceed(); // VULNERABLE — proceeds despite certificate error
    }
});

// Pattern 5 — OkHttp with a permissive TrustManager
OkHttpClient client = new OkHttpClient.Builder()
    .sslSocketFactory(sslSocketFactory, (X509TrustManager) trustAllCerts[0])
    .hostnameVerifier((hostname, session) -> true) // VULNERABLE
    .build();
```

## Vulnerable patterns — Kotlin

```kotlin
// Pattern 1 — trust-all TrustManager
val trustAllCerts = arrayOf<TrustManager>(object : X509TrustManager {
    override fun getAcceptedIssuers(): Array<X509Certificate> = arrayOf()
    override fun checkClientTrusted(chain: Array<X509Certificate>, authType: String) {}
    override fun checkServerTrusted(chain: Array<X509Certificate>, authType: String) {} // VULNERABLE
})
val sslContext = SSLContext.getInstance("TLS")
sslContext.init(null, trustAllCerts, SecureRandom())

// Pattern 2 — hostname verifier always true
val client = OkHttpClient.Builder()
    .hostnameVerifier { _, _ -> true } // VULNERABLE — accepts any hostname
    .build()

// Pattern 3 — combined trust-all + verify-all in one client (common copy-pasted snippet)
val client = OkHttpClient.Builder()
    .sslSocketFactory(insecureSocketFactory, trustAllCerts[0] as X509TrustManager)
    .hostnameVerifier { _, _ -> true }
    .build() // VULNERABLE — both checks disabled
```

## False positive patterns — do not flag these

```java
// FALSE POSITIVE 1 — real certificate pinning, not a bypass
// The TrustManager does perform validation logic, just against a pinned cert
public void checkServerTrusted(X509Certificate[] chain, String authType) throws CertificateException {
    if (!chain[0].equals(pinnedCertificate)) {
        throw new CertificateException("Certificate does not match pinned certificate");
    }
    // SAFE — validation logic is present and throws on mismatch
}

// FALSE POSITIVE 2 — default system TrustManagerFactory (correct usage)
TrustManagerFactory tmf = TrustManagerFactory.getInstance(TrustManagerFactory.getDefaultAlgorithm());
tmf.init((KeyStore) null); // SAFE — uses the platform's default trust store
SSLContext sc = SSLContext.getInstance("TLS");
sc.init(null, tmf.getTrustManagers(), new SecureRandom());

// FALSE POSITIVE 3 — default hostname verifier explicitly restored (correct usage)
connection.setHostnameVerifier(HttpsURLConnection.getDefaultHostnameVerifier()); // SAFE

// FALSE POSITIVE 4 — WebView correctly rejecting on SSL error
webView.setWebViewClient(new WebViewClient() {
    @Override
    public void onReceivedSslError(WebView view, SslErrorHandler handler, SslError error) {
        handler.cancel(); // SAFE — connection is refused on certificate error
    }
});

// FALSE POSITIVE 5 — trust-all TrustManager gated behind BuildConfig.DEBUG
// Flag as WARNING only, not CRITICAL — must not reach production
if (BuildConfig.DEBUG) {
    sc.init(null, trustAllCerts, new SecureRandom()); // WARNING — not CRITICAL, but must be removed before release
}
```

## Secure alternatives

```java
// Option 1 — use the platform default trust manager (recommended default)
TrustManagerFactory tmf = TrustManagerFactory.getInstance(TrustManagerFactory.getDefaultAlgorithm());
tmf.init((KeyStore) null);
SSLContext sc = SSLContext.getInstance("TLS");
sc.init(null, tmf.getTrustManagers(), new SecureRandom());
HttpsURLConnection.setDefaultSSLSocketFactory(sc.getSocketFactory());
// Never override setDefaultHostnameVerifier — let the platform default apply

// Option 2 — certificate pinning via Android Network Security Config
// res/xml/network_security_config.xml declares the pinned cert; no code changes needed
// AndroidManifest.xml: android:networkSecurityConfig="@xml/network_security_config"

// Option 3 — OkHttp CertificatePinner (correct pinning, not a bypass)
CertificatePinner pinner = new CertificatePinner.Builder()
    .add("api.paymentbackend.com", "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .build();
OkHttpClient client = new OkHttpClient.Builder()
    .certificatePinner(pinner)
    .build(); // Default TrustManager and HostnameVerifier remain active

// Option 4 — WebView: always cancel on SSL error, never proceed
webView.setWebViewClient(new WebViewClient() {
    @Override
    public void onReceivedSslError(WebView view, SslErrorHandler handler, SslError error) {
        handler.cancel();
    }
});
```

```kotlin
// Kotlin — platform default trust manager
val tmf = TrustManagerFactory.getInstance(TrustManagerFactory.getDefaultAlgorithm())
tmf.init(null as KeyStore?)
val sslContext = SSLContext.getInstance("TLS")
sslContext.init(null, tmf.trustManagers, SecureRandom())

// Kotlin — OkHttp certificate pinning
val pinner = CertificatePinner.Builder()
    .add("api.paymentbackend.com", "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .build()
val client = OkHttpClient.Builder()
    .certificatePinner(pinner)
    .build() // Do not add a custom hostnameVerifier or trust manager alongside this
```
