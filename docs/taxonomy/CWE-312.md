# CWE-312 — Cleartext storage of sensitive information (SAD persistence)

**Severity:** CRITICAL
**Frequency in Android payment code:** Low-Medium
**Languages:** Java, Kotlin

---

## Description

CWE-311's taxonomy entry already lists CWE-312 as its storage-specific child
weakness, and covers the general case: sensitive data (passwords, PAN,
tokens) written to disk without encryption. That general rule treats
encryption as the fix — once a value is encrypted before it's persisted, it
is no longer flagged.

This entry covers a narrower and stricter case that CWE-311's "encrypt it
and it's fine" rule does not capture: **Sensitive Authentication Data
(SAD)**, a defined term under PCI SSF Module A. For a fixed set of fields —
full magnetic-stripe/track data, the card verification value (CAV2/CVC2/
CVV2/CID), and the PIN or PIN block — PCI SSF Module A.1 does not require
protection, it prohibits storage after authorization **under any
circumstances, even encrypted**. There is no secure way to persist these
specific fields once a transaction has been authorized; the only correct
behavior is to never write them anywhere durable in the first place.

### Why encryption doesn't fix this

Every other CWE in this taxonomy treats encryption as the remedy: a hardcoded
key becomes safe once generated properly (CWE-798), a weak IV becomes safe
once randomized (CWE-329), plaintext storage becomes safe once encrypted
(CWE-311/312 general case). CWE-312 SAD persistence is different — encrypting
a CVV before writing it to a database does not make the code compliant. The
requirement is about the field itself never surviving past the authorization
step, not about how well it's protected while it does.

### Scope — which fields trigger this rule

| Field | Trigger? | Notes |
|---|---|---|
| Full track / magnetic-stripe data | Yes | Includes chip-equivalent full track data |
| CVV2 / CVC2 / CAV2 / CID (card verification value) | Yes | The 3-4 digit code printed on the card, never the PAN itself |
| PIN / PIN block | Yes | Cleartext PIN or the encrypted PIN block structure used in transit |
| PAN (card number) | **No** | PAN storage is permitted if rendered unreadable — that's CWE-311's general "missing encryption" rule, not this one |
| Expiry date, cardholder name | No | Not classified as SAD; ordinary CWE-311 sensitivity applies |

If the field being persisted is a PAN, password, or other general sensitive
value — not one of the three SAD fields above — this is not CWE-312 SAD
persistence. Route it to CWE-311 instead (missing encryption is the correct
and sufficient fix there).

### Direct PCI SSF relevance

PCI SSF Module A.1 states this is an absolute prohibition, not a "protect
it" requirement: sensitive authentication data must never be stored after
authorization, regardless of whether it is encrypted, hashed, or truncated.
An assessor who finds a CVV field, PIN, or full track data written to a
database, file, log, or SharedPreferences anywhere in the codebase treats it
as a direct Module A.1 failure — the encryption status of that write is
irrelevant to the finding.

## Detection logic

**Flag when (always CRITICAL, regardless of encryption):**
- A variable/field clearly identified as CVV, CVC2, CVV2, CAV2, or CID
  (card verification value) is written to SharedPreferences, a file, a
  database (`ContentValues`/SQLite insert, Room entity persistence), or a
  log statement
- A PIN or PIN block value is written to any of the same persistent sinks
- Full track/magnetic-stripe data (`track1Data`, `track2Data`,
  `magneticStripeData` or equivalent) is written to any persistent sink
- This applies even if the value is passed through an encryption or hashing
  call first — encrypting a SAD field before persisting it is still a
  Module A.1 violation, not a mitigation

**Do NOT flag:**
- The same fields used transiently in memory during the live authorization
  flow and never written to a persistent sink (variable assignment, method
  parameter passing, or use directly inside an API request body sent
  synchronously as part of authorization) — this is expected and required
  for the transaction to complete
- PAN, expiry date, or cardholder name written to storage — even
  unencrypted, this is CWE-311's territory, not CWE-312 SAD persistence
  (though it should still be flagged there)
- A comment indicating the value is discarded/zeroed immediately after use
  and never actually reaches a storage call
- Methods named `goodG2B`, `goodG2B2`, `goodB2G` — Juliet secure patterns,
  do not flag

**Confidence:** always `high` when a SAD field name is directly visible in
a persistence call — this rule has no legitimate exception once storage is
confirmed, unlike CWE-311 where encryption changes the verdict.

## Detection difficulty for SAST tools

| Pattern | Regex detects? | LLM detects? | Why |
|---|---|---|---|
| `values.put("cvv", cvv); db.insert(...)` | Partial | Yes | Must recognize `cvv` as a SAD field, not just any sensitive string |
| `prefs.edit().putString("pin_block", pinBlock)` | Partial | Yes | Same — field-name semantics, not just a persistence API call |
| `values.put("cvv", encrypt(cvv))` | No | Yes | Regex would treat this as "already encrypted, safe" — an LLM must know encryption doesn't exempt SAD fields |
| CVV used only in an in-memory auth request object | N/A | Yes | Must distinguish transient use from persistence — regex has no concept of "does this reach disk" |
| `track2Data` written to a crash-report log | No | Yes | Requires recognizing the log call as a persistent sink and the field as SAD |

**CryptoGuard advantage:** the encrypted and unencrypted versions of a SAD
write look almost identical to a regex ("value ends up in a DB/file call")
but have the same verdict either way — this is one of the few CWEs in the
taxonomy where the LLM's job is not to distinguish safe from unsafe
encryption, but to recognize that encryption is irrelevant to the verdict at
all.

## Vulnerable patterns — Java

```java
// Pattern 1 — CVV persisted to SQLite, unencrypted
ContentValues values = new ContentValues();
values.put("card_number", cardNumber);
values.put("cvv", cvv); // VULNERABLE — CVV must never be stored, encrypted or not
db.insert("payments", null, values);

// Pattern 2 — CVV encrypted before storage (still a violation — SAD, not PAN)
String encryptedCvv = encryptWithAesGcm(cvv, secretKey);
values.put("cvv", encryptedCvv); // VULNERABLE — encryption does not exempt SAD fields
db.insert("payments", null, values);

// Pattern 3 — PIN block written to SharedPreferences
prefs.edit().putString("pin_block", pinBlock).apply(); // VULNERABLE — PIN data must never persist

// Pattern 4 — full track data written to a file for "debug" purposes
FileOutputStream fos = openFileOutput("last_swipe.log", MODE_PRIVATE);
fos.write(track2Data.getBytes()); // VULNERABLE — full track data on disk

// Pattern 5 — CVV logged for troubleshooting
Log.d("PaymentDebug", "Validating CVV: " + cvv); // VULNERABLE — SAD field in a persistent log
```

## Vulnerable patterns — Kotlin

```kotlin
// Pattern 1 — CVC2 stored in Room entity
@Entity
data class TransactionRecord(
    val cardNumber: String,
    val cvc2: String, // VULNERABLE — persisted to the Room database on every insert
    val amount: Double
)

// Pattern 2 — PIN cached to SharedPreferences "for convenience"
prefs.edit().putString("cached_pin", pin).apply() // VULNERABLE — PIN must never persist

// Pattern 3 — hashed CVV still a violation
val hashedCvv = BCrypt.hashpw(cvv, BCrypt.gensalt())
prefs.edit().putString("cvv_hash", hashedCvv).apply() // VULNERABLE — hashing does not exempt SAD fields
```

## False positive patterns — do not flag these

```java
// FALSE POSITIVE 1 — CVV used transiently in the live authorization request only
public AuthResponse authorize(String pan, String cvv, String expiry) {
    AuthRequest req = new AuthRequest(pan, cvv, expiry);
    return backendClient.sendSync(req); // SAFE — CVV never written to any persistent sink
}

// FALSE POSITIVE 2 — PAN stored, unencrypted (still wrong, but it's CWE-311, not CWE-312)
values.put("card_number", cardNumber); // Flag as CWE-311, not CWE-312 — PAN is not SAD

// FALSE POSITIVE 3 — CVV explicitly discarded after the authorization call
public void processPayment(String cvv) {
    boolean approved = gateway.charge(cvv);
    cvv = null; // SAFE — no persistence call anywhere in this method
}

// FALSE POSITIVE 4 — non-SAD transaction metadata stored
values.put("transaction_id", txId);
values.put("timestamp", System.currentTimeMillis()); // SAFE — not a SAD field
db.insert("transactions", null, values);
```

```kotlin
// FALSE POSITIVE 5 — CVV passed to authorization, but a DIFFERENT object is persisted
// The CVV variable and a persistence call both appear in this method, but the CVV
// is never an argument to the persistence call itself — only the token is.
fun authorizeAndStore(dao: TransactionDao, pan: String, cvv: String, expiry: String) {
    val authResponse = gateway.authorize(pan, cvv, expiry) // cvv used here only
    dao.insert(TransactionRecord(cardNumber = pan, token = authResponse.token)) // SAFE — cvv is not in this call
}
```

## Secure alternatives

```java
// Option 1 — never assign SAD fields to a variable that outlives the auth call
public AuthResponse authorize(PaymentRequest request) {
    // request.getCvv() is read once, embedded directly in the outbound request, then goes out of scope
    return backendClient.sendSync(buildAuthPayload(request));
}

// Option 2 — if a field absolutely must be referenced after authorization, store a token instead
// Payment processors issue a token/reference in the auth response — persist the token, never the CVV/PIN/track data
values.put("payment_token", authResponse.getToken()); // SAFE — token has no SAD value if leaked

// Option 3 — explicitly zero PIN buffers after use (defense in depth, not a substitute for never persisting)
char[] pinBuffer = readPinFromPad();
try {
    processPin(pinBuffer);
} finally {
    Arrays.fill(pinBuffer, '\0');
}
```

```kotlin
// Kotlin — token-based persistence instead of SAD fields
val authResponse = gateway.authorize(pan, cvv, expiry)
db.insert(TransactionRecord(cardNumber = pan, token = authResponse.token))
// cvv is never referenced again after the authorize() call — nothing to persist
```
