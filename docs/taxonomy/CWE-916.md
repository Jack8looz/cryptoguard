# CWE-916 — Use of password hash with insufficient computational effort

**Severity:** CRITICAL  
**Frequency in Android payment code:** High  
**Languages:** Java, Kotlin  

---

## Description

Password hashing is fundamentally different from data hashing. When hashing
files, messages, or certificates for integrity checking, a fast algorithm like
SHA-256 is correct and desirable. When hashing passwords for storage and
later verification, speed is the enemy — a fast hash allows an attacker with
a GPU to compute billions of guesses per second against a leaked database.

**The core rule:** SHA-256, SHA-512, and MD5 are never acceptable for password
hashing, even though SHA-256 and SHA-512 are considered cryptographically
secure for other purposes.

Purpose-built password hashing algorithms solve this by being deliberately
slow and memory-intensive:

- **Argon2:** winner of the Password Hashing Competition (2015). OWASP's top
  recommendation. Configurable time, memory, and parallelism parameters.
- **bcrypt:** adds a configurable work factor. Cost 10 means ~100ms per hash.
  Increasing cost by 1 doubles the computation time. Widely supported.
- **scrypt:** memory-hard. Requires large amounts of RAM in addition to CPU
  time, defeating GPU-based attacks.
- **PBKDF2:** older but acceptable. Built into Java with no extra dependency.
  Requires a minimum of 310,000 iterations for PBKDF2-SHA256 per OWASP 2023.

## Attack feasibility — 2025 hardware

This table shows why fast hashes are unacceptable for passwords. Numbers
are based on 8× RTX 4090 GPUs, which represent a realistic attacker budget:

| Hash type | Hashes/second | Time to try 1 billion passwords |
|---|---|---|
| MD5 | 200 billion | 0.005 seconds |
| SHA-256 | 23 billion | 0.04 seconds |
| SHA-512 | 8 billion | 0.1 seconds |
| bcrypt (cost=10) | ~50,000 | 5.5 hours |
| bcrypt (cost=12) | ~12,500 | 22 hours |
| Argon2 (standard) | ~5,000 | 2.3 days |

**Conclusion:** a single GPU cluster can crack a SHA-256 password database
in seconds. The same hardware cracks bcrypt cost=12 at ~12,500 attempts per
second — still faster than ideal for weak passwords, but 1.8 million times
slower than SHA-256. Argon2 pushes this further to 2.3 days per billion
attempts, making brute-force attacks economically infeasible for strong passwords.

For a payment terminal application where PINs and authentication credentials
are stored, this difference is the line between a catastrophic breach and
a contained incident.

## Detection logic — context-based, not algorithm-based

This CWE requires flexible, context-aware detection. SHA-256 is not always
a vulnerability — it depends entirely on what is being hashed.

**Flag as CWE-916 when SHA-256, SHA-512, MD5, or any fast hash is applied
to something that appears to be a password or PIN.**

Signals that indicate password context:

| Signal type | Examples |
|---|---|
| Variable name | `password`, `passwd`, `pwd`, `pin`, `userPin`, `userInput` |
| Method context | `login()`, `authenticate()`, `verifyPassword()`, `checkPin()` |
| Class name | `AuthService`, `LoginManager`, `UserRepository`, `PinVerifier` |
| Database storage | result stored in `password_hash`, `user_password`, `pin_hash` |
| Comparison pattern | hash compared against a stored value from a users table |

**Do not flag when SHA-256 is used for:**
- File integrity checking
- Certificate fingerprinting
- JKS/KeyStore operations
- Message authentication codes (HMAC)
- Non-password data hashing
- Android KeyStore hardware-backed key derivation

### Work-factor variant — correct KDF, insufficient parameter (PCI SSF 7.4.b)

The rule above covers the case where the wrong primitive is used entirely
(SHA-256/MD5 instead of a password-hashing KDF). A separate case is using
the *right* primitive (PBKDF2, bcrypt, scrypt) with a work-factor parameter
too low to resist brute force. This is still CWE-916 — insufficient
computational effort — never CWE-328 (which is specifically about a missing
or predictable salt, not the iteration count).

**Flag as CWE-916 (HIGH) when:**
- `PBEKeySpec(password, salt, iterations, keyLength)` — the `iterations`
  argument is a numeric literal below 310,000 (OWASP 2023 minimum for
  PBKDF2-HmacSHA256). PCI SSF 7.4.b's own floor is lower (10,000) — anything
  below 310,000 is flagged here since it also necessarily fails PCI's floor
  once it drops below 10,000, and 310,000 is the actual bar this taxonomy
  enforces
- `BCrypt.gensalt(cost)` — the `cost` argument is below 10
- `SCrypt` with an explicit CPU/memory cost parameter (`N`) below 16384 (2^14)
- The KDF call has no explicit iteration/cost argument and relies on a
  library default that is itself below these thresholds

**Do NOT flag when:**
- `PBEKeySpec` iteration count is 310,000 or higher
- `BCrypt.gensalt(cost)` with cost 10 or higher (`BCrypt.gensalt()` with no
  argument defaults to 10 in most implementations — treat as safe)
- `SCrypt` with N at 16384 or higher
- Argon2 with any explicit parameters — Argon2's defaults are already tuned
  above the vulnerable range for this taxonomy's purposes

## Why an LLM detects this better than regex

A regex tool cannot distinguish:

```java
// These two lines are identical — only context tells them apart
MessageDigest.getInstance("SHA-256").digest(input.getBytes())
```

- In `checkFileIntegrity()` → safe, fast hash is correct
- In `verifyUserPassword()` → CWE-916, must use bcrypt/Argon2

An LLM reads the method name, variable names, class name, and surrounding
logic to determine whether `input` is a password or a file. No pattern
matching tool can make this distinction reliably.

### Note on JKS files

The development team uses JKS (Java KeyStore) files for certificate and key
management. SHA-256 and SHA-1 appear legitimately inside JKS operations for
certificate fingerprinting and key derivation — these must NOT be flagged as
CWE-916. The AI must recognize KeyStore context as a false positive.

## Vulnerable patterns — Java

```java
// Pattern 1 — SHA-256 applied directly to a password
byte[] hash = MessageDigest.getInstance("SHA-256")
                           .digest(password.getBytes());

// Pattern 2 — SHA-512 applied to a password (still wrong — too fast)
byte[] hash = MessageDigest.getInstance("SHA-512")
                           .digest(password.getBytes());

// Pattern 3 — MD5 for password hashing (broken AND fast — doubly wrong)
byte[] hash = MessageDigest.getInstance("MD5")
                           .digest(password.getBytes());

// Pattern 4 — PBKDF2 with insufficient iteration count
SecretKeyFactory skf = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256");
PBEKeySpec spec = new PBEKeySpec(password, salt, 1000, 256);
// 1000 iterations is far below the OWASP minimum of 310,000

// Pattern 5 — SHA-256 in a login/authenticate method
public boolean authenticate(String username, String password) {
    String hash = sha256(password); // CWE-916 — context makes it clear
    return hash.equals(storedHash);
}
```

## Vulnerable patterns — Kotlin

```kotlin
// Pattern 1 — direct SHA-256 on password variable
val hash = MessageDigest.getInstance("SHA-256")
    .digest(password.toByteArray())

// Pattern 2 — extension function hiding the weak hash
fun String.hashPassword(): ByteArray =
    MessageDigest.getInstance("SHA-256").digest(toByteArray()) // CWE-916

// Pattern 3 — extension property hiding the vulnerability
val String.sha256Hash: String
    get() = MessageDigest.getInstance("SHA-256")
        .digest(toByteArray()).toString() // Still CWE-916

// Pattern 4 — data class with default value using weak hash
// Easy to miss in code review due to Kotlin's concise syntax
data class User(
    val username: String,
    val passwordHash: String = sha256("default123") // CWE-916
)

// Pattern 5 — PBKDF2 with low iteration count
val spec = PBEKeySpec(password.toCharArray(), salt, 1000, 256) // Too few iterations
```

## False positive patterns — do not flag these

```java
// FALSE POSITIVE 1 — SHA-256 for file integrity (not a password)
byte[] fileHash = MessageDigest.getInstance("SHA-256")
                               .digest(fileBytes); // Safe

// FALSE POSITIVE 2 — SHA-256 for JKS certificate fingerprint
MessageDigest md = MessageDigest.getInstance("SHA-256");
byte[] fingerprint = md.digest(certificate.getEncoded()); // Safe

// FALSE POSITIVE 3 — HMAC-SHA256 for message authentication
Mac mac = Mac.getInstance("HmacSHA256");
mac.init(secretKey);
byte[] hmac = mac.doFinal(message); // Safe — not password hashing

// FALSE POSITIVE 4 — KeyStore load operation
KeyStore ks = KeyStore.getInstance("JKS");
ks.load(stream, passphrase.toCharArray()); // Safe — JKS internal operation

// FALSE POSITIVE 5 — PBKDF2 with sufficient iterations
PBEKeySpec spec = new PBEKeySpec(password, salt, 310000, 256); // Safe — OWASP 2023

// FALSE POSITIVE 6 — Android KeyStore with hardware backing
// Hardware-backed key derivation is secure by design
import android.security.keystore.KeyGenParameterSpec;
KeyGenParameterSpec spec = new KeyGenParameterSpec.Builder(
    "my_key",
    KeyProperties.PURPOSE_ENCRYPT | KeyProperties.PURPOSE_DECRYPT)
    .setUserAuthenticationRequired(true)
    .build();
// The secure element handles key derivation — this is not CWE-916
```

## Secure alternatives — OWASP priority order

```java
// Option 1 — Argon2 (OWASP #1 recommendation, strongest)
// Add dependency: de.mkammerer:argon2-jvm:2.11
Argon2 argon2 = Argon2Factory.create();
// Parameters: iterations=3, memory=65536KB, parallelism=1
String hash = argon2.hash(3, 65536, 1, password.toCharArray());
boolean matches = argon2.verify(hash, password.toCharArray());
// Always clear password from memory after use
argon2.wipeArray(password.toCharArray());

// Option 2 — bcrypt (excellent, widely supported)
// Add dependency: org.mindrot:jbcrypt:0.4
// Cost 12 is recommended — cost 10 is the minimum acceptable
String hashed = BCrypt.hashpw(password, BCrypt.gensalt(12));
boolean matches = BCrypt.checkpw(password, hashed);

// Option 3 — PBKDF2 (acceptable, built into Java — no extra dependency)
// Use only if Argon2 and bcrypt cannot be added as dependencies
SecretKeyFactory skf = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256");
byte[] salt = new byte[16];
new SecureRandom().nextBytes(salt);
PBEKeySpec spec = new PBEKeySpec(
    password.toCharArray(),
    salt,
    310000,   // OWASP 2023 minimum for PBKDF2-SHA256
    256
);
byte[] hash = skf.generateSecret(spec).getEncoded();
spec.clearPassword(); // Always clear the PBEKeySpec after use
```
